### Fixed - a message decrypted but not yet stored can no longer be lost to a checkpoint or an early acknowledgement

A checkpoint now waits for every frame between its decrypt and its row before it exports, a failed live row write (an upgrade of a notification's caption, an edit, a deletion included) is kept and retried, and an application frame is acknowledged only once ITS rows are stored - every row a decrypted frame writes carries that frame's id, so one unstorable row no longer withholds every acknowledgement; a row the store itself refuses at its request (`RowRefusedError` with `DataError`/`DataCloneError`) is dropped at ERROR instead of stalling the device, and a message whose dispatch throws after its decrypt is kept for the next checkpoint instead of being taken for a decrypt failure ([chat](docs/wiki/frontend/modules/chat.md#rows-before-ratchet-the-decrypt-half-and-the-ack-2026-11-19)).
