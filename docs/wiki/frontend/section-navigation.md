# Section navigation - going deeper instead of showing every tab (CLOSED 2026-10-14)

Requested by the user on 2026-10-08, after reading both existing patterns on a phone: *"Le but n'est pas d'avoir des menus caches"*, and *"on navigue en profondeur"*, like a file explorer or Android's Settings, with at most a path (`Associations > BDE - Bureau des Eleves > Partenariats`).

## CLOSED 2026-10-14 - the final shape, do not reopen

Every menu of the app was inventoried on 2026-10-14 (every route under `frontend/src/routes`, every `$state` holding a tab, every `role="tablist"`, every `overflow-x-auto`) and each one now has ONE of two shapes. A change that adds a third shape is a regression, and `lib/styles/sectionMenus.test.ts` fails on it; the rule is in [durable-rules](../durable-rules.md#ui-and-i18n---frontendarchitecture-auth-native-prompts).

| Shape | When | Where |
| --- | --- | --- |
| **Hub of route sections** under a breadcrumb | more than 3 entries, or entries gated per reader | the app's own hub (`/dashboard`, no breadcrumb: it is a tab), association edit (`/associations/<slug>/edit/<section>`), association and list public page (`/associations/<slug>/<section>`, `/lists/<slug>/<section>`), list edit, administration (`/admin/<page>`), account settings (`/settings/<section>`), own profile (`/profile/me/<section>`) |
| **Fixed segmented control** (`ui/SegmentedControl.svelte`) | 3 or so short labels | shop (products, partnerships), moderation (3), legacy dues (4, `text-xs` below `sm`), salon settings (2), community admin panel (2-3), conversation media panel (3), new conversation (2) |

How each shape behaves:

- **A hub** is `navigation/SectionHub.svelte` (rows = links: icon, title, a summary where a count is already loaded, chevron) with ONE table per area deciding both the row and the route guard (`editSections`, `publicSections`, `adminSections`, `settingsSections`, `profileSections`): a section the reader may not open, or that does not exist, is sent back to the hub. `navigation/Breadcrumb.svelte` draws the path, every crumb a link, the last one the title, the back arrow the previous crumb; a phone folds the middle behind an ellipsis. **The same hub on a wide screen** - no rail. A section is a route: Back goes up one level, a reload keeps the place, a link can be shared, a section is `noindex` (the hub stays the ONE indexable page of a public association).
- **A segmented control** shows every entry at 320 px (equal `minmax(0, 1fr)` columns, icon above a label that may wrap, never icon-only), carries tablist semantics, and adds NO history entry: a page's segment lives in `?tab=` through `navigation/tabQuery.ts`, written with SvelteKit's `replaceState`, so a reload keeps it and Back leaves the page; a panel's segment is local `$state` and the panel stays one entry of `historyOverlayStack`.
- **History**: a section moves through SvelteKit navigation, an overlay through `historyOverlayStack`, and nothing else writes the History API (the gate enforces it). Back therefore reads one model: router entries for places, overlay entries for what covers them (#1817).

**Decided by the user (2026-10-08 to 2026-10-10)**: every menu, in lots; no persistent rail on wide screens (the same hub as on a phone); every crumb clickable; hub rows with a summary; 3 or fewer short labels stay a fixed control, more become a hub; `/profile` is a hub too, with `me` as the segment that keeps a section key from competing with a user id.

**Refused, and why**: a scrolling strip (entries past the edge are unreachable and nothing says they exist); a wrapped grid of tabs (half a phone screen that never retracts); icon-only segments; a history entry per segment (Back would walk through tabs instead of leaving the page); an optional `[[section]]` for settings (it would drop `/settings` from the static routes).

**Not menus, and left as they are**: the notifications all/unread pills and the posts feed pills (filters of one list, drawn the way the design reference draws them, `flex-wrap`, never clipped); the emoji picker's category row (a tool row inside a picker); the data tables and attachment carousels that scroll on purpose (listed under lot 4).

**`/dashboard` is the app's hub (UI-1 of the 2026-10-16 UI redesign audit, #1958).** It was a launcher of tiles (`goto` buttons, a theme toggle, a red sign-out tile as the largest target on the screen). It is now `SectionHub` groups from ONE table, `lib/navigation/dashboardSections.ts`, the same column on a phone and a desktop: the identity row (avatar, name, "Voir mon profil"), **Explorer** (agenda, associations, lists, institutions, shop, forms, notifications with `postNotifStore.unread` as a count pill, the directory only for a reader who reaches `/admin` - where its only link was), **Mes associations** (live memberships holding a right, `isAdmin`, the association page's own test for its "Manage" link; a list's goes to `/lists/<slug>/edit`), **Administration** (`ensureMayOpenAdmin`, titled by `adminScopeLabels`), **Documents** for a reviewer (a headingless row), **Compte** (settings, sign-out last). The table only LINKS: no page's own guard changed. **Each kind is its OWN section, never mixed (2026-10-18, user: "que les associations ici")**: "Mes associations" holds associations only, then "Mes listes" and "Mes institutions", each hidden when empty, by `groupAssociationsForSelect` (the ONE classifier every picker uses). Two layouts, both split: the dashboard's row lists (`DashboardGroupKey` `managed` / `managedLists` / `managedInstitutions`, rows leading with the organisation's logo - `HubRow.logo`, drawn by `AssociationAvatar` - or its kind glyph Users / Building2 / Landmark without a logo URL) and `/associations`' card grid (`mineSections`, `AssociationTile` with its logo). Tested in `dashboardSections.test.ts` and `routes/dashboard/page.svelte.test.ts`. Owed: a look on a phone and a desktop. Two extensions of `HubRow` came with it, both optional: `onSelect` (an ACTION row, a button with no chevron - sign-out is the one gesture that is not a place; `HubLinkRow` is the type of every other hub) and `badge`/`avatarUserId`. The theme toggle is gone (`/settings/preferences` carries the three-way choice) and `themeStore.cycle()` with it. The admin group draws no visible heading (its one row already carries `adminScope.title()`). The count pill is `aria-hidden` with an `sr-only` sentence beside it. The page calls `postNotifStore.load()` on mount (its only other loader is the bell, mounted on the Feed alone on a phone, so the count was missing on a cold open and stale after one; `load()` drops a call in flight, no timer added). Sign-out goes through `signOutByChoice()` in `stores/auth.ts`, shared with the navbar: a failure is logged as an error and told in a toast instead of vanishing in a click handler's `void`. **Speed and stability**: identity, Explorer and Compte render on the first frame from held state, gated by no probe: **sign-out is always reachable**, including when a probe never answers (a token refresh has no deadline today; that is being fixed in `auth.ts` separately). The probed groups (Mes associations, Administration, the reviewer's Documents - moved out of Compte so its arrival cannot push sign-out down - and the staff Annuaire row) wait for `Promise.allSettled` over the three probes and are then inserted ABOVE Compte all at once; a probe that rejects settles too and hides only what it gates (logged). **No space is reserved for them**: a one-row placeholder was tried and, for the commonest reader (a member, who gets no probed group), it collapsed and Compte jumped UP about 80 px, so a tap aimed at Settings landed on Sign-out. With nothing reserved, the only shift is DOWNWARD, once, for a manager or staff, and none for a member; a downward shift cannot bring sign-out under a finger. While the probes run, an `sr-only` `role="status"` says "Chargement" to assistive technology and takes no layout; a probe that hangs leaves only that. For a platform admin `ensureMayOpenAdmin` short-circuits, so the probe is one background `GET /api/associations/me/list` for that tier alone (shared, five-minute `SharedCache`). **Every hub's row now WRAPS its label (hyphenated) and keeps two lines of summary**, where both were `truncate`: at 200 % text a 390 px row cut the reader's own name to "Ada Lov...". Tested in `routes/dashboard/page.svelte.test.ts` (member, manager, staff, reviewer, the pill, the sign-out row). Read in a local Chrome against a fixture API (no estate touched; dev serves only pre-releases) at 390 and 1280, light and dark, and 390 at a doubled root font: no horizontal scroll, sign-out clears the tab bar. NOT read: the real bench accounts on dev (needs a pre-release), the unread pill on screen (the store fills only where the bell is mounted, the Feed on a phone). `/forms` by role (a member's forms to fill vs "Mes formulaires" for a manager) is NOT in this: the page lists only the reader's own forms and no endpoint lists the forms open to a member, so it is UI-6. Owed: both phones (first paint of the tab, no shift above Explorer when groups 3-4 arrive, Android Back from a row, the native tab bar).

**Owed, and it does not reopen the chantier**: one look on each phone (a hub, one section, Back and the Android hardware back, a reload on a section), one row in [backlog](../backlog.md#owed-a-verification-and-nothing-else).

## How it was built, lot by lot

**Lot 1 SHIPPED: the shared foundation and the edit page** (`routes/associations/[slug]/edit/[[section]]`). User decisions of 2026-10-08: scope is EVERY menu in the app, in lots; **no persistent rail on wide screens** (the same hub as on a phone - this supersedes point 4 below); the path A > B > C has EVERY crumb clickable, the last being the title, and the back arrow is the previous crumb; hub rows carry icon, title, a summary where a count is already loaded (members) and a chevron.

What exists now, to reuse in the next lots:

- `lib/components/navigation/Breadcrumb.svelte` (+ `breadcrumb.ts`: `previousCrumb`, `foldedCrumbCount`, the `HubRow` type): arrow, then the path; on a phone the middle folds behind an ellipsis, a wide screen shows it all. `PageHeader` takes `crumbs` in place of `backHref`.
- `lib/components/navigation/SectionHub.svelte`: rows as real links (`data-hub-row`), no strip so no `data-swipe-nav-ignore`.
- `lib/associations/editSections.ts`: the section keys, `editRights`, `mayOpenEditSection` (the ONE rule the hub and the route both ask), `editTrail` (the path, hence the Back behaviour of every level), `editSectionHref`.
- `[[section]]/+page.ts` redirects `?section=<key>` (notification deep links, the form-creation return, the post-creation landing) to the segment, an unknown name to the hub. The three producers now write the segment themselves.
- **The permission gap is closed**: a typed `/edit/danger` used to open whatever `EDIT_SECTIONS` allowed; the page now sends a section its reader may not open back to the hub once the roster is known (the server was already the authority on every write). Tested in `editSections.test.ts`.
- `seo/resolve.ts` `ASSOCIATION_EDIT_PATH` accepts the segment.
- Back behaviour is pinned per level (section -> hub -> public page -> directory) by `editSections.test.ts` and `SectionNavigation.svelte.test.ts`. `frontend/` has no Playwright setup, so the router-level reading (browser Back, reload on a section, an Android hardware back) is a **manual check owed on both phones**.

**Lot 2 (branch `feat/section-hub-public`, DRAFT PR): the public page and the list edit page.**

- `lib/associations/publicSections.ts` is to the public page what `editSections.ts` is to the edit page: keys (`calendar`, `members`, `shop`, `partnerships`; the about text is the hub's own body), `mayOpenPublicSection` (shop and partnerships exist only with content - a typed `/shop` on an association with nothing to sell is sent back to the hub), `publicTrail`, `publicSectionHref`, `publicSectionWidth` (calendar, shop, partnerships `grid`; hub and members `tool`) and `publicRedirectTarget`.
- Routes: `/associations/[slug]/[[section]]` and `/lists/[slug]/[[section]]` render the same `AssociationDetailView`; navigating between hub and section reuses the component, so the data is NOT reloaded. The identity card (follow, manage) belongs to the hub; a section shows the path and its own card. Hub rows come first, the about text below.
- `?section=calendar&fromPost=<id>` (PostCard) is redirected by `+page.ts` to `/associations/<slug>/calendar?fromPost=<id>`; the calendar still reads `fromPost` itself. `?section=about` and an unknown name land on the hub.
- **SEO: the hub stays the ONE indexable page.** A section is `noindex` in the page `load` AND in `resolveSeoForPath` (`ASSOCIATION_SECTION_PATH`, built from the section keys, so the server answer carries it too), is not in the sitemap, and lists are already under the private `/lists` prefix. - Verified in headless Chrome at 390 and 1280 against a fixture API (hub, every row, browser Back, the arrow, reload on a section, the legacy link, shop with and without products, unknown segment, list public and edit): no horizontal scroll, every Back goes up one level. ## Traps already found

- **The edit page renders a requested section its user may not see**: `editSection` is validated against the static `EDIT_SECTIONS`, not against the `canManage*` permissions. Route segments must authorise per section on the server and the client. Check this FIRST.
- `data-swipe-nav-ignore` exists because strips must not turn the global tab swipe; a hub has no strip, so it goes with the strips, but the sticky `-mx-4` containers and `.page-scroll-wrap` (`will-change: transform`, containing block of `fixed`) must be re-read.
- Any `pushState` goes through `historyOverlayStack` or SvelteKit navigation, never raw: ghost entries are what the stack's `skipPops` exists for.
- `aria-label="Edit sections"` is a hard-coded English string; the new component is Paraglide from its first draft.
- Back behaviour is a GATE, not an impression: a test per level (section -> hub -> parent -> previous page), and one reading on both phones.
