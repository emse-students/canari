# Section navigation - going deeper instead of showing every tab (CLOSED 2026-10-14)

Requested by the user on 2026-10-08, after reading both existing patterns on a phone: *"Le but n'est pas d'avoir des menus caches"*, and *"on navigue en profondeur"*, like a file explorer or Android's Settings, with at most a path (`Associations > BDE - Bureau des Eleves > Partenariats`).

## CLOSED 2026-10-14 - the final shape, do not reopen

Every menu of the app was inventoried on 2026-10-14 (every route under `frontend/src/routes`, every `$state` holding a tab, every `role="tablist"`, every `overflow-x-auto`) and each one now has ONE of two shapes. A change that adds a third shape is a regression, and `lib/styles/sectionMenus.test.ts` fails on it; the rule is in [durable-rules](../durable-rules.md#ui-and-i18n---frontendarchitecture-auth-native-prompts).

| Shape | When | Where |
| --- | --- | --- |
| **Hub of route sections** under a breadcrumb | more than 3 entries, or entries gated per reader | the app's own hub (`/dashboard`, no breadcrumb: it is a tab), association edit (`/associations/<slug>/edit/<section>`), association and list public page (`/associations/<slug>/<section>`, `/lists/<slug>/<section>`), list edit, administration (`/admin/<page>`), account settings (`/settings/<section>`), own profile (`/profile/me/<section>`) |
| **Fixed segmented control** (`ui/SegmentedControl.svelte`) | 3 or so short labels | shop (products, partnerships), moderation (3), legacy dues (4, `text-xs` below `sm`), salon settings (2), community admin panel (2-3), conversation media panel (3), new conversation (2), the Emojis preference in `/settings/preferences` (2, [emoji](emoji.md#the-setting---one-resolver-2026-11-09)) |

How each shape behaves:

- **A hub** is `navigation/SectionHub.svelte` (rows = links: icon, title, a summary where a count is already loaded, chevron) with ONE table per area deciding both the row and the route guard (`editSections`, `publicSections`, `adminSections`, `settingsSections`, `profileSections`): a section the reader may not open, or that does not exist, is sent back to the hub. `navigation/Breadcrumb.svelte` draws the path, every crumb a link, the last one the title, the back arrow the previous crumb; a phone folds the middle behind an ellipsis. **The same hub on a wide screen** - no rail. A section is a route: Back goes up one level, a reload keeps the place, a link can be shared, a section is `noindex` (the hub stays the ONE indexable page of a public association).
- **A segmented control** shows every entry at 320 px (equal `minmax(0, 1fr)` columns, icon above a label that may wrap, never icon-only), carries tablist semantics, and adds NO history entry: a page's segment lives in `?tab=` through `navigation/tabQuery.ts`, written with SvelteKit's `replaceState`, so a reload keeps it and Back leaves the page; a panel's segment is local `$state` and the panel stays one entry of `historyOverlayStack`.
- **History**: a section moves through SvelteKit navigation, an overlay through `historyOverlayStack`, and nothing else writes the History API (the gate enforces it). Back therefore reads one model: router entries for places, overlay entries for what covers them (#1817).

**Decided by the user (2026-10-08 to 2026-10-10)**: every menu, in lots; no persistent rail on wide screens (the same hub as on a phone); every crumb clickable; hub rows with a summary; 3 or fewer short labels stay a fixed control, more become a hub; `/profile` is a hub too, with `me` as the segment that keeps a section key from competing with a user id.

**Refused, and why**: a scrolling strip (entries past the edge are unreachable and nothing says they exist); a wrapped grid of tabs (half a phone screen that never retracts); icon-only segments; a history entry per segment (Back would walk through tabs instead of leaving the page); an optional `[[section]]` for settings (it would drop `/settings` from the static routes).

**Not menus, and left as they are**: the notifications all/unread pills and the posts feed pills (filters of one list, drawn the way the design reference draws them, `flex-wrap`, never clipped); the emoji picker's category row (a tool row inside a picker); the data tables and attachment carousels that scroll on purpose (listed under lot 4).

## Traps already found

- **The edit page renders a requested section its user may not see**: `editSection` is validated against the static `EDIT_SECTIONS`, not against the `canManage*` permissions. Route segments must authorise per section on the server and the client. Check this FIRST.
- `data-swipe-nav-ignore` exists because strips must not turn the global tab swipe; a hub has no strip, so it goes with the strips, but the sticky `-mx-4` containers and `.page-scroll-wrap` (`will-change: transform`, containing block of `fixed`) must be re-read.
- Any `pushState` goes through `historyOverlayStack` or SvelteKit navigation, never raw: ghost entries are what the stack's `skipPops` exists for.
- `aria-label="Edit sections"` is a hard-coded English string; the new component is Paraglide from its first draft.
- Back behaviour is a GATE, not an impression: a test per level (section -> hub -> parent -> previous page), and one reading on both phones.

- **A DESCENDANT THAT CALLS `stopPropagation()` ON `touchstart` BLINDS A BUBBLE LISTENER (#84, read 2026-11-14 on the Mi 9T).** `svelte-dnd-action` does it on every draggable row it owns - the channel rows of a community the viewer MANAGES - so on `/communities` a section swipe that began on such a row never reached the shell: no gesture state, no claim, the browser's pan took the move (`pointercancel`, then non-cancelable moves). A non-manager, or a cold start before the roles loaded, swiped fine, which is why it looked intermittent. The shell therefore hears the start in the CAPTURE phase (`bindSwipeNavTouchListeners`, pinned by `swipeNavigation.test.ts`).
- **A swipe never outlives a reorder.** Because the shell hears the touch start in the capture phase, a drag of a channel row (`delayTouchStart: 350`) or a community-rail icon is also a swipe the shell tracks. `standDownForDndDrag` (`swipeNavigation.ts`) abandons the swipe, and snaps back anything already claimed, as soon as svelte-dnd-action's dragged clone (`#dnd-action-dragged-el`) exists. A swipe over a row or a rail icon that has not been picked up navigates like on every other surface (lead decision, 2026-11-14).

## Back after a cross-section open returns to the origin (owner report, 2026-11-15)

**Defect against the closed design, not a reopening.** On an iPhone, feed -> a post's association chip -> the arrow of the association page landed on the Associations list, not on the feed (recording read frame by frame: the page showed the path `Associations > Humani'Mines`, the arrow went to its first crumb). "Back goes up one level" is right when the reader went DOWN the tree; it is wrong when a link from elsewhere dropped them inside it.

**Mechanism.** The page header's arrow is an `<a href>` to the structural parent: the previous crumb (`Breadcrumb.svelte`, trail tables) or `backHref` (`PageHeader.svelte`). It never looked at history. The Android hardware back, the iOS edge swipe and the browser Back already walk history, so they were right; only the arrow disagreed.

**The rule, once, no case per link** (`lib/navigation/backToOrigin.ts`, `historyEntry.ts`): every link or goto that ADDS a history entry records the page it left against THAT ENTRY, in a module `Map` keyed by SvelteKit's own `navigationIndex` (read out of `history.state`; a push is +1, a replace keeps it, Back and Forward restore the entry's own; `historyEntry.test.ts` reads SvelteKit's source so an upgrade that renames it fails there). **It lives as long as the document: a reload starts empty and the arrow then follows its structural link** (an earlier comment said it survived a reload; it never did). **Nothing navigates to record it** - review of #3648: the first version stamped `page.state` through a shallow replacing `goto`, which in SvelteKit 3 is a SECOND navigation (it bumps the navigation token, runs every `beforeNavigate`/`onNavigate` subscriber again, and aborts a mount-time guard redirect or a tap that lands inside it). A Back arrow carries `data-back-link` (`Breadcrumb.svelte`, and `PageHeader.svelte`'s `backHref` link) and `handleAppLinkClick` (`utils/openExternal.ts`, the document-level capture listener that already decides EVERY in-app link click) asks `backDecision(current, from, up)`: **history Back** when `from` is the structural parent or in ANOTHER top-level section (first path segment), **the structural link** otherwise. **Trap found by reading it in a browser**: a first version bound an `onclick` on the anchor and never ran, because that listener already cancels and navigates every in-app link before the anchor hears it. The `href` stays for assistive technology; a modified or non-primary click never reaches the decision.

**A replace records nothing and INHERITS the replaced entry's origin.** Sign-in, the auth callback, `returnTo`, a mount-time guard redirect, an error recovery or the /lives to /posts redirect replace the entry they run on; the page they came from is not in history. Recording it made a cold deep link after sign-in call `history.back()` into nothing (a dead arrow, and on iOS and Tauri the arrow is the only Back), and let an association page's own redirect overwrite a correct cross-section origin. A replace is recognised by the key not moving; it also drops the offset of the page it overwrote.

**One-shot forms are never a destination, and they are declared, not guessed** (`ONE_SHOT_FORM_ROUTES` in `backToOrigin.ts`, review #2 of #3648): a creation form is gone once submitted, so a list created at `/associations/new` and landing on `/lists/<slug>` must not offer to reopen it. The first version matched a path SEGMENT (`create`, `new`, `edit`), a branch on route names with false positives (`/associations/[slug]/edit/[[section]]` and `/lists/[slug]/edit/[[section]]` are durable management hubs, and a slug called `new` would match). The list now holds SvelteKit ROUTE IDS (`/associations/new`, `/institutions/new`, `/lists/new`, `/forms/create`), the entry records the route id of the page it left next to its address, and a test fails on an id no route directory carries. A new creation route is added to that list. **Post creation has nothing to declare**: there is no `/posts/new`, the composer is an overlay on `/posts` and never enters history. The edit forms of forms and booking spaces are not declared (a Back to them is harmless); declare one if that changes. Call sites read: `AssociationCreatePage`, `forms/create` (to `/posts`, no arrow), `admin/carte` (same section).

**With an overlay open the arrow follows its link**: an open sheet owns a ghost history entry (`historyOverlayStack`), so `history.back()` would close the sheet and leave the page, an arrow that looks dead; the link is a navigation whose `beforeNavigate` drains the stack.

**Back also restores the page's offset** (`lib/navigation/scrollMemory.ts`): the app scrolls inside ONE box (`.page-scroll-wrap`), which SvelteKit's window restoration does not see, so any Back to the feed landed on its top. The layout records the box's offset against the ENTRY as it is left (two `/posts` entries keep two offsets) and puts it back on a `popstate` only (a link opens a page at its top). The wait is events, no clock: the offset is applied when the box is tall enough AND shows no placeholder (a list skeleton declares itself with `data-loading-skeleton`: `posts`, `posts/[postId]`, `notifications`, `directory`, `admin/moderation`. NOT `animate-pulse` or `aria-busy`, which a live card's dot, a stuck per-image loader or a busy button also wear for ever, so a feed with one live card never restored: review #2 of #3648); it ends at the first of: applied; a change after which no placeholder is left and two animation frames pass with no further change (settled shorter: the browser clamps - a feed that mounts cards a frame at a time keeps invalidating that check); ANY `scroll` event while it waits (it never scrolls the box before applying, so such an event is the reader's: wheel, touch, key, scrollbar); the next navigation. A ResizeObserver on the box and a MutationObserver on its subtree see late children. The two layout hooks are `navigationMemory.ts` (`onLeavingEntry`, `onArrivedAtEntry`), skipped for a SHALLOW navigation of any type, and tested as a sequence.

**The place is an anchor plus an offset (next pre-release, [entry, closed by the S5 readings](../device-verification.md#the-phone-readings-of-2026-11-18-s5-170-alpha12-the-alpha12-fixes-on-both-phones)).** On the Mi 9T the feed left at 1500 css px came back at 1726. A `scrollTop` is a distance in the layout it was measured in, and the feed's layout can differ between leave and return (cards mount a few at a time, the suggestions strip arrives, images and posters settle to their height). **UNVERIFIED HYPOTHESIS: the layout above the post was taller at the restore than when the reader left, so the stored number pointed at another post.** Not measured; Chrome's scroll anchoring is NOT claimed to add the growth (and `overflow-anchor` is left alone). The entry therefore also records an anchor: the first `data-scroll-anchor="<id>"` element of the box whose bottom is below the box's top (a feed card wears its post id; found by a binary search, O(log n) layout reads), and its distance from the box's top. The restore waits for THAT element (a tall page that lacks the post is not ready), scrolls until it sits at that distance, then keeps it aligned with NO proof of alignment: **the first version ended on the anchor confirmed within a pixel on two consecutive frames, and the Mi 9T (`1.7.0-alpha.5`) then read the post 8 to 13 px low, because content arrived ABOVE it after the proof (most likely a link preview or poster fetched when the cards above came near the viewport; the answer lands whenever it lands, so any proof is met too early by construction)**. Now every resize, mutation or `load` callback re-aligns it synchronously (a ResizeObserver callback runs after layout and before paint, so the move is never painted) and only an EVENT ends the restore: the reader's wheel, touch, pointer or key input, the next navigation, another programmatic scroll, a FOREIGN scroll (a scroll event whose scrollTop is not the one the restore last wrote: find-in-page, a focus, a screen reader), or the anchor leaving the page (no jump to the offset, no warning). A feed with a live dot costs a rect read per mutation and no frame loop. An anchor never reached ends on two consecutive frames with an unchanged scrollable height, as the logged fallback. **What reports a change**: the box has a FIXED height and never resizes, so a ResizeObserver on it alone sees nothing; the restore observes the box's first child, the list holding the anchor and the anchor itself, a MutationObserver watches the subtree, and capture-phase `load` / `loadedmetadata` / `error` listeners on the box catch an image or poster settling without any DOM change. The anchor is resolved once and reused while it stays connected (a plain id is one attribute selector, not a scan per mutation; an id with quotes, brackets or control characters is compared as a string, never escaped into a selector that could throw in an observer). **What ends it**: the reader's wheel, touch, pointer or key event, on the box or on the document (the restore now scrolls the box itself, so a `scroll` event can no longer prove the reader; before the anchor is aligned it still does), the next navigation, and any other programmatic scroll (`scrollPageToTop`, `resetPageScroll` call `cancelRestore`, kept in `restoreControl.ts` so `scrollToTop.ts` need not import the module that imports it). Chosen over "wait for the layout to be stable" because stability has no observable end: an image that never loads keeps the page unstable. No timer anywhere. A page with no anchor and an anchor whose post is gone (deleted meanwhile, re-ranked "Pour toi", beyond the loaded page) keep the raw offset; the second is a FALLBACK and is logged with `Log.w` naming the anchor. **Only the feed (`/posts`, every tab: Pour toi, Organisations are feed tabs) wears anchors**; the directory, notifications and the other lists keep the raw offset.
