## 3. What the measurement found that is a DEFECT, not a cost

These are gaps in what the suite catches, found while measuring it. They come first in the plan
because they are cheap and each one has already let something through, or can.

1. **`docsMergeArtefacts.test.ts` guards `changelog.d/` and `docs/` but lives in the frontend job,
   which a docs-only pull request does not trigger** (`run-frontend` names `frontend/**`, `libs/**`
   and a few configs, never `changelog.d/` or `docs/`). A malformed fragment or a write under
   `[Unreleased]` in a docs-only PR merges green. The rule belongs in `.github/scripts/tests`, which
   runs on every PR.
2. **The production frontend is built on `main` only**, so a dependency bump that breaks the build
   is green on its PR and red after merge: run 38950147816 on `main` failed in `adapter-node`
   (`Cannot read properties of undefined (reading 'base')`) after its PR passed.
3. **Every runner accepts an empty gate**: `--passWithNoTests` on the frontend and on all four jest
   scripts. A broken `include` glob or a renamed directory turns a suite into a green no-op.
4. **The 5 s default `testTimeout` measures the machine, not the code** for the first test of a file
   that imports lazily: 10 such timeouts in one local subset run, none at 4 workers. This is the
   "wall clock in a test" rule broken by default configuration rather than by any one test.
5. **`CLAUDE.md` says `main`'s own CI takes "~8 min after a merge"**; measured push runs on `main`
   took 17-20 min (39079347726: 20 min, 39050300633: 18 min). The release preflight's "wait for
   `CI passed`" advice is short by more than half.

## 4. The principles every work package is held to

1. **A test earns its place by catching a class of defect no other layer catches.** For each
   candidate deletion, name the class, name the layer that still catches it, or keep the test.
2. **A gate fails loudly on an empty gate.** No `--passWithNoTests`; a scan that finds zero files
   is a failure (`markupSources` already asserts "is reading the tree it thinks it is" - every scan
   does the same).
3. **Never assert a wall clock.** No `waitFor` budget that a slow runner can exceed, no first-test
   import paid inside a per-test timeout. Fake timers, or a predicate with the default budget and
   the cost moved out of the test.
4. **A case is a behaviour, not a file.** A lint rule applied to 1,850 files is ONE assertion that
   lists its offenders, not 1,850 cases. The count is a reading the user takes; it must mean
   something.
5. **A source-text test is the last resort and says why** (several already do:
   `startupOrder.test.ts`, `pinFirstSetupRefuted.test.ts`). One that does not say why is triaged.
6. **A test lives in the job that runs when the thing it guards changes.** A test reading `docs/`
   cannot live in a job gated on `frontend/`.
7. **Speed comes from the setup, not from deleting tests.** The test bodies are 5 % of the time;
   deleting tests to go faster deletes coverage for a rounding error.
8. **Every change to the rig that alters what a runner READS invalidates its green rows** (rule 33,
   [cross-client-harness-findings](cross-client-harness-findings.md)), so rig refactors are batched
   and re-run together, never trickled.

## 5. The work packages, in order

Ranked by (minutes saved + flake removed) against risk. Size: S under a day, M a few days, L a
week or a campaign session. "Revalidate" says what must be re-run after the WP and what the harness
must re-prove; **none of WP-T1 to WP-T6 changes a byte the app ships, so none of them owes a harness
row** - they are proven by the suite itself, by the counts below and by a deliberately broken
change failing.

### WP-T1 (S) - Paraglide `locale-modules` for the tests only

- **Change**: a second compile (`outputStructure: 'locale-modules'`) into a test-only directory,
  aliased as `$lib/paraglide` in `vitest.config.ts` ahead of `$lib`; the app build keeps
  `message-modules` (it tree-shakes per message). `bun run test` compiles both.
- **Removes**: ~70 % of the frontend step (measured on 125 files: 236 s to 64-72 s). Expected CI
  step: 16 min to ~5 min; ~1,000 runner-minutes a day. Also removes the 5 s first-test timeouts of
  section 3.4 at the source.
- **Risk**: low. Same messages, same runtime, same locale switch; only the module layout differs.
  Guard it: one test asserting that the alias resolves to the test output, and that a key missing
  from it fails (so the two compiles cannot drift silently).
- **Revalidate**: full suite green with the same case count (11,534 +/- what merged meanwhile);
  `bun run build` output unchanged, since the app still compiles `message-modules`.

### WP-T2 (S) - Gates that fail on empty, and tests in the job that runs them

- **Change**: drop `--passWithNoTests` from the frontend and the four jest scripts; move
  `docsMergeArtefacts.test.ts` (and any other `src/*.test.ts` that reads only `docs/`,
  `changelog.d/` or repo files - check `lineEndings`, `googleVerification`, `svelteConfigStamp`) to
  `.github/scripts/tests` as `bun` scripts wired into `test-ci-scripts`
  (`recipe-covers-tests.test.mjs` then enforces the wiring); build the production frontend on PRs
  that touch `frontend/package.json`, `bun.lock`, `patches/`, `kit.config.js` or `vite.config.js`
  (+0.7 min on those PRs only).
- **Removes**: defects 3.1, 3.2 and 3.3. Minutes: none; this WP buys catches.
- **Risk**: none for behaviour. Revalidate: a docs-only PR with a bad fragment goes red; a jest
  `testMatch` pointing nowhere goes red.

### WP-T3 (S) - One case per rule, not per file

- **Change**: `serverProse.test.ts` and `markupSources.test.ts` (and the 14 smaller `it.each` over a
  directory listing) become one `it` per rule that collects every offender and fails with the full
  list. Keep each scan's "is reading the tree it thinks it is" assertion.
- **Removes**: ~3,300 cases (11,534 to ~8,200) with no class lost; the count starts meaning
  behaviours. Minutes: negligible.
- **Risk**: none if the failure message still lists every file. Revalidate: plant one offender in
  each scan, see it named.

### WP-T4 (M) - `node` environment by default, `happy-dom` only where a test needs a DOM

- **Change**: vitest `projects`: `*.svelte.test.ts` and an explicit list (the ~209 files touching
  `document`/`mount`) on `happy-dom`, everything else on `node`. Seed the list from a
  `--environment=node` run (78 % of the subset already passes under node), never by guessing.
- **Removes**: after WP-T1 the environment is 56-60 % of what is left on the subset; expect a
  further -30 to -50 % of the step. Fewer happy-dom globals also means fewer tests passing by
  accident on a DOM they never meant to use.
- **Risk**: low-medium: a test that silently relied on `window` for a fallback. Revalidate: same
  case count, same pass set, and the list of moved files in the PR.

**Built 2026-10-18 (draft PR `chore/tests-t4-node-env`).** `vitest.config.ts` says
`environment: 'node'`, and the **391** files (2026-10-24) that need a DOM say so on their own first line:
`// @vitest-environment happy-dom`. The population was SEEDED from `--environment=node` runs, never
guessed: 149 plain test files (the first whole-suite run) and 150 of the 179 `*.svelte.test.ts` (a
second run of those alone; the other 29 pass under node and now run there), plus 3 that `main` added
before the merge and that the node default turned red at once, as designed. The merge of 2026-10-23 seeded 70 more the same way, from one whole-suite run under node: every one failed on a missing DOM global or on an assertion over a `typeof window` arm, none on a timeout. One more passed its tests under node and still read `localStorage` AFTER them (16 unhandled rejections on CI): a seeding run must read the unhandled errors too, not only the failed tests. Of the 150, 142 failed
on a missing global and 8 on an ASSERTION - code that branches on `typeof window` took its other arm
(`useChannelWorkspaces`, `.offlineWrites`, `useConversations.currentConvoScope`,
`feedPaintIdentity`, `signedFeedUrl`, `displayName.reactive`, `displayNames`, `memberOrder`). Both
are red, which is what seeding needs; the residual risk is the third kind, a test that PASSES under
node on a non-DOM arm, which no seeding run can see - those files assert what they now run.

**A pragma per file, not a list, and why.** The first version named the 149 plain files in a
`vitest.dom-files.ts` beside the config. The pragma won on three counts: it travels with the file (a
rename or a move keeps it, where a list entry goes stale and an entry for a deleted file stays for
ever, silently); it puts the decision where the reader of the test is; and **a central sorted list of
149 to 299 paths is one block every parallel pull request appends to**, the exact conflict
`changelog.d/` was created to remove, and a conflict here blocks the automatic merge. Its one cost is
real and is guarded: vitest takes the FIRST match of the pragma ANYWHERE in a file's text
(`detectCodeBlock`), comments and strings included, so a test that merely MENTIONED it would move
onto happy-dom without a word.

**Revalidated by a permanent guard, and by breaking it twice.** `src/test/environment.test.ts` carries
no pragma, so it runs where a new DOM test that forgot the line would: it asserts there is no
`document`/`window` and that a DOM call throws `document is not defined`, and it scans every test
file for the pragma anywhere but line 1, exactly spelled. Its twin `environment.dom.test.ts` pins that
the pragma is honoured. Deliberate breaks, then restored: the pragma removed from
`clickOutside.test.ts` turned all 13 of its cases red with `ReferenceError: document is not
defined`; the pragma moved to line 2 of `portal.test.ts` made the scan name that file. Same cases
(8,449 on `main`, +3 guards = 8,452), same pass set; `check` 0 errors, `lint` and `format` clean.

**Time: NO CLAIM, measured locally under load.** One interleaved pair on this machine with other
agents running: happy-dom everywhere 370 s wall (10 files failing), node by default 395 s (14
failing); the first version's pair read 733 s vs 641 s mean. The noise is larger than the effect, so
nothing is concluded locally. On CI, the pull request's first run (list version) took 10.6 min in
`Test Frontend (Svelte)`, against 7.4-12.7 min (most near 11.6) for the 19 other frontend jobs of the
same morning: inside the spread. The delta is owed to a few CI runs of this branch against `main`'s.

**What the runs found, owed to WP-T6.** Every local failure in both pairs is vitest's 5 s
`testTimeout`, and most are WHOLE-TREE SCANS doing their walk inside a test (`accent`,
`toastLocalization`, `apiUrl.absolute`, `ModalOverlay`, `versionProbeOnUnlockPath`,
`useNotifications.singleBuilder`, `sectionMenus`, `groupSweep`, `conversations.retire`): each
re-walks `src/` on its own, and `accent`'s scan alone takes 3.9 s here. Re-run alone, 5 of 6 such
files were green and `accent` was not - a wall clock measuring the machine, which is WP-T6's class,
and one shared, memoised file list is the fix it points at.

### 7.2 The declared copies, deleted (2026-10-21)

The first deletion step of WP-TEST-TOOLING-REFORM, the one 7.1 called defensible. **Ten of the eleven
`declared-copy` rows were deleted; one was kept, with its reason written into the group.**

**The rule, now in the header of `.github/scripts/lib/declared-duplicates.mjs`: a copied module needs
ONE spec, not one per copy.** An `exact` group pins every copy of the module to the same bytes, so the
spec beside the group's FIRST file proves all of them; a byte-identical spec beside each other copy ran
the same assertions on the same text. The old reason for the copies ("or three services assert the
behaviour and the fourth only inherits the file") was true of the spec and false of the behaviour: the
fourth file IS the first file, and `declared-duplicates.test.mjs` fails on one changed byte (shown on
2026-10-21 by changing `once` to `on` in social-service's `drain-on-sigterm.ts`: `FAIL ... 1 of 3
cop(y|ies) drifted`, naming the file). That gate runs in `make test-ci-scripts`, on every pull request.

**Kept: `http-error-log.spec.ts` in BOTH core and social.** The module is duck-typed (no `axios`
import), but its spec builds an `AxiosError` from the `axios` THAT service resolved, and each service
has its own `bun.lock`: an `axios` bump in one service only could change the error's shape under that
service's copy, and the other service's spec would not see it. The property is a secret not reaching a
log, so the copy earns its place. Its group carries `keepEachCopy: true`, which `tools/test-inventory`
reads so the row stops being proposed.

**Why `@nestjs/common` did not keep the others, said honestly.** Version skew is NOT what separates
them: Dependabot's `nestjs` group also moves per service directory, so one service's Nest can differ
from another's exactly as its `axios` can. What differs is what the spec feeds the module. The
`http-error-log` spec hands the duck-typed renderer an OBJECT BUILT BY THE DEPENDENCY (`config`,
`headers`, `response`), whose shape is the very thing the renderer reads, and it guards a secret leak.
The deleted specs use `@nestjs/common` only for a `Logger` and the CLASS an exception is thrown as -
the module and its spec import that class from the same package, so the assertion cannot diverge
between services unless Nest changes what `new UnauthorizedException()` / `new BadRequestException()`
is. **That is the residual risk, named:** a Nest major landing in one service that changed those
exception classes or `Logger` would no longer be seen by a spec in THAT service. What still stands in
front of it is that service's `framework-boot.spec.ts` (the `@nestjs/*` tree coheres and boots), its
other specs that throw the same classes, and the human review the auto-merge ceiling forces on every
major. Judged implausible enough not to keep nine copies for it.
