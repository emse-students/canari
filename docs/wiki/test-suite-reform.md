# Test suite reform - the measured estate and the plan (2026-10-18)

> **Status: PLAN, nothing changed yet.** Asked by the user on 2026-10-18 (*"la refonte de tout
> l'outillage me semble necessaire et peut-etre faite maintenant. On est a un nombre de test aberrant
> je crois."*). Every number below was MEASURED on that date - from `gh run view` job data, the CI
> logs' own summaries, or a same-machine A/B run - and says where it comes from. Re-measure before
> believing one that is more than a few weeks old.
>
> Related: [testing-methodology](testing-methodology.md) (how a result earns belief),
> [cicd](cicd.md) (the jobs), [cross-client-harness-findings](cross-client-harness-findings.md)

| 5 | **~133 CI runs a day** (300 runs in 54 h, 200 `pull_request` + 100 `push`), the frontend suite running in about two thirds of them: **~1,400 runner-minutes a day**, and every merged change pays it twice (pull request, then `main`) | `gh run list --limit 300` |

**The flake picture is better than feared.** In 300 CI runs there was ONE rerun and ZERO flaky
failures: all 20 red runs were real (a type error in a spec, a dead wiki anchor, a dependency whose
patch no longer applied, a production build broken on `main`, a branch's own test). The known
flakes are LOCAL and share one cause: the first test of a file pays the file's lazy imports inside
vitest's 5 s `testTimeout`, so on a loaded 16-core machine `pinChange` "killed half way",
`salonRowClock`, `readWatermarkCache`, `gifSearch`, `editSession` and others time out (10 timeouts in
one local run of the 125-file subset; none at 4 workers). Number 3 removes most of that import cost,
so it is also the flake fix.

## 3. What the measurement found that is a DEFECT, not a cost

These are gaps in what the suite catches, found while measuring it. They come first in the plan
because they are cheap and each one has already let something through, or can.

1. **`docsMergeArtefacts.test.ts` guards `changelog.d/` and `docs/` but lives in the frontend job,
   which a docs-only pull request does not trigger** (`run-frontend` names `frontend/**`, `libs/**`
   and a few configs, never `changelog.d/` or `docs/`). A malformed fragment or a write under
   `[Unreleased]` in a docs-only PR merges green. The rule belongs in `.github/scripts/tests`, which
   runs on every PR.
2. **The production frontend is built on `main` only**, so a dependency bump that breaks the build
   is green on its PR and red after merge: run 38950147816 on `main` failed in `adapter-node`
   (`Cannot read properties of undefined (reading 'base')`) after its PR passed.
3. **Every runner accepts an empty gate**: `--passWithNoTests` on the frontend and on all four jest
   scripts. A broken `include` glob or a renamed directory turns a suite into a green no-op.
4. **The 5 s default `testTimeout` measures the machine, not the code** for the first test of a file
   that imports lazily: 10 such timeouts in one local subset run, none at 4 workers. This is the
   "wall clock in a test" rule broken by default configuration rather than by any one test.
5. **`CLAUDE.md` says `main`'s own CI takes "~8 min after a merge"**; measured push runs on `main`
   took 17-20 min (39079347726: 20 min, 39050300633: 18 min). The release preflight's "wait for
   `CI passed`" advice is short by more than half.

## 4. The principles every work package is held to

1. **A test earns its place by catching a class of defect no other layer catches.** For each
   candidate deletion, name the class, name the layer that still catches it, or keep the test.
2. **A gate fails loudly on an empty gate.** No `--passWithNoTests`; a scan that finds zero files
   is a failure (`markupSources` already asserts "is reading the tree it thinks it is" - every scan
   does the same).
3. **Never assert a wall clock.** No `waitFor` budget that a slow runner can exceed, no first-test
   import paid inside a per-test timeout. Fake timers, or a predicate with the default budget and
   the cost moved out of the test.
4. **A case is a behaviour, not a file.** A lint rule applied to 1,850 files is ONE assertion that
   lists its offenders, not 1,850 cases. The count is a reading the user takes; it must mean
   something.
5. **A source-text test is the last resort and says why** (several already do:
   `startupOrder.test.ts`, `pinFirstSetupRefuted.test.ts`). One that does not say why is triaged.
6. **A test lives in the job that runs when the thing it guards changes.** A test reading `docs/`
   cannot live in a job gated on `frontend/`.
7. **Speed comes from the setup, not from deleting tests.** The test bodies are 5 % of the time;
   deleting tests to go faster deletes coverage for a rounding error.
8. **Every change to the rig that alters what a runner READS invalidates its green rows** (rule 33,
   [cross-client-harness-findings](cross-client-harness-findings.md)), so rig refactors are batched
   and re-run together, never trickled.

## 5. The work packages, in order

Ranked by (minutes saved + flake removed) against risk. Size: S under a day, M a few days, L a
week or a campaign session. "Revalidate" says what must be re-run after the WP and what the harness
must re-prove; **none of WP-T1 to WP-T6 changes a byte the app ships, so none of them owes a harness
row** - they are proven by the suite itself, by the counts below and by a deliberately broken
change failing.

### WP-T1 (S) - Paraglide `locale-modules` for the tests only

- **Change**: a second compile (`outputStructure: 'locale-modules'`) into a test-only directory,
  aliased as `$lib/paraglide` in `vitest.config.ts` ahead of `$lib`; the app build keeps
  `message-modules` (it tree-shakes per message). `bun run test` compiles both.
- **Removes**: ~70 % of the frontend step (measured on 125 files: 236 s to 64-72 s). Expected CI
  step: 16 min to ~5 min; ~1,000 runner-minutes a day. Also removes the 5 s first-test timeouts of
  section 3.4 at the source.
- **Risk**: low. Same messages, same runtime, same locale switch; only the module layout differs.
  Guard it: one test asserting that the alias resolves to the test output, and that a key missing
  from it fails (so the two compiles cannot drift silently).
- **Revalidate**: full suite green with the same case count (11,534 +/- what merged meanwhile);
  `bun run build` output unchanged, since the app still compiles `message-modules`.

### WP-T2 (S) - Gates that fail on empty, and tests in the job that runs them

- **Change**: drop `--passWithNoTests` from the frontend and the four jest scripts; move
  `docsMergeArtefacts.test.ts` (and any other `src/*.test.ts` that reads only `docs/`,
  `changelog.d/` or repo files - check `lineEndings`, `googleVerification`, `svelteConfigStamp`) to
  `.github/scripts/tests` as `bun` scripts wired into `test-ci-scripts`
  (`recipe-covers-tests.test.mjs` then enforces the wiring); build the production frontend on PRs
  that touch `frontend/package.json`, `bun.lock`, `patches/`, `svelte.config.js` or `vite.config.js`
  (+0.7 min on those PRs only).
- **Removes**: defects 3.1, 3.2 and 3.3. Minutes: none; this WP buys catches.
- **Risk**: none for behaviour. Revalidate: a docs-only PR with a bad fragment goes red; a jest
  `testMatch` pointing nowhere goes red.

### WP-T3 (S) - One case per rule, not per file

- **Change**: `serverProse.test.ts` and `markupSources.test.ts` (and the 14 smaller `it.each` over a
  directory listing) become one `it` per rule that collects every offender and fails with the full
  list. Keep each scan's "is reading the tree it thinks it is" assertion.
- **Removes**: ~3,300 cases (11,534 to ~8,200) with no class lost; the count starts meaning
  behaviours. Minutes: negligible.
- **Risk**: none if the failure message still lists every file. Revalidate: plant one offender in
  each scan, see it named.

### WP-T4 (M) - `node` environment by default, `happy-dom` only where a test needs a DOM

- **Change**: vitest `projects`: `*.svelte.test.ts` and an explicit list (the ~209 files touching
  `document`/`mount`) on `happy-dom`, everything else on `node`. Seed the list from a
  `--environment=node` run (78 % of the subset already passes under node), never by guessing.
- **Removes**: after WP-T1 the environment is 56-60 % of what is left on the subset; expect a
  further -30 to -50 % of the step. Fewer happy-dom globals also means fewer tests passing by
  accident on a DOM they never meant to use.
- **Risk**: low-medium: a test that silently relied on `window` for a fallback. Revalidate: same
  case count, same pass set, and the list of moved files in the PR.

### WP-T5 (M) - Triage the source-text tests

- **Change**: each file gets one disposition, written in its header: (a) rewrite as a behavioural
  test through a real seam; (b) turn into a lint rule (`oxlint`/`oxvelte`) if it is a pattern ban;
  (c) keep, with the "why a source test" paragraph if missing; (d) delete when a behavioural test
  already catches the same class (name it in the PR).
- **Removes**: the brittleness class "a refactor that keeps behaviour breaks a test" and the
  opposite one, "a renamed variable keeps a dead test green". 35 native-contract tests (Kotlin,
  Swift, manifests) are OUT of scope: no other layer catches them short of a device build.
- **Risk**: medium (each deletion needs its covering test named). Revalidate per file; for (a), show
  the new test failing on the bug the old one was written for.

### 7.1 The reading

Written by hand against the block above; the numbers it quotes are that block's.

- **The count is not duplication.** 27 flags out of 1,443 files, and only the 11 `declared-copy` rows
  (65 cases, half a percent of the static count) are redundant by the repository's own admission. The
  "aberrant number" is carried by `it.each` expansion (7,975 static cases against 8,770 run) and by
  how many suites there are, which is what WP-T1/T3/T4 already address; deleting tests would not move
  it, which is principle 7 above, measured.
- **The 11 `declared-copy` rows are the only deletions the repository could defend today.** The four
  NestJS services each keep a byte-identical copy of `drain-on-sigterm`, `cors-origins` and the
  `internal-token` guard, and `.github/scripts/tests/declared-duplicates.test.mjs` already pins those
  sources identical, so one service's spec covers the others' copies. Cost of removing the other
  copies: a few seconds of jest and an edit to `DECLARED_GROUPS`; gain: 65 cases. `framework-boot.spec.ts`
  is NOT among them: each copy asserts what is installed in its own service.
- **WP-T5 held up.** The 6 `source-text` rows that its keep list does not name were each read: they are
  repo-wide guards with a defect behind them (`paraglideMessages`, `paraglideTestAlias`, `noRealSleeps`,
  `appThemeTransition`, `tooltipOneKey`) or a dependency-bump guard that was RED in CI on 2026-10-16

  contract tests: merge their shared case with an `it.each`, do not delete.
- **Red history is thin evidence.** 43 files were named in the last 60 failed CI runs and one run
  accounts for 30 of them; 715 files were born in a fix commit. Both say "this guarded something once",
  neither says "this is safe to remove", so a deletion review starts from `bornInFix` and `ciRed`.
