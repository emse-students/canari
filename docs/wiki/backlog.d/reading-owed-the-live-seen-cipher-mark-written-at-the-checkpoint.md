## P2 - a frame read before a browser kill is called "never read here" on the next cold start

target: 1.7.0

**What is built:** the live seen-cipher mark written at the checkpoint (#1998, `v1.3.0`).

**Measured on 2026-11-14** (TAB-3b, two runs, local estate at `ad2053fc0`, a fresh W1+W2 group): both outage messages arrived exactly once, but the SECOND cold start logged `[History] frame never read here and unreadable for good (secret-reuse); will reconcile` for the frame W1 had read in the first run (`SecretReuseError`: the ratchet had consumed it, so it WAS read here). The mark of a frame read shortly before a hard kill (the process is stopped, no lifecycle event) does not survive to the next load. The reading that closed the entry - no new such line on a cold start after a drain - therefore FAILS; what is owed is the cause (is the mark written only by the checkpoint the kill pre-empted?) and a rerun of TAB-3b reading zero lines.

**Web rig, 2026-11-16 (dev `1.7.0-alpha.2`, W6 alpha and W7 beta, a fresh three-member group): NOT REPRODUCED in 3 runs, cause still not established.** The shape of TAB-3b on two seats it can use: W6's browser crashed (`killBrowser`, a process stop), beta sent while it was down, W6 relaunched and its drain read the frame (the marker rendered), W6 crashed again 0-1 s after that read (plus the kill's own 1-2 s), relaunched, and its console was scanned for 30 s for `never read here`, `unreadable for good` and `SecretReuse`: 0 lines on the first start and 0 on the second in all three runs (273, 309 and 293 console lines on the first starts). **What the code says about the entry's question** (read, not run): since the KILL-2 fix of 2026-10-26 the seen set lives in the MLS state, not in `localStorage` (`stageSeenCipherHashes`, staged by `stagePendingHistoryMarks` into the checkpoint's export), so a mark is durable exactly when the checkpoint that carries it lands. `noteFrameConsumed` runs AFTER `processIncomingMessage` returns (`openDistributionFrame`, and the live path), so a checkpoint made INSIDE the decrypt advances the ratchet without the mark, and the mark waits for the next checkpoint: a crash between the two leaves a spent generation with no mark - the shape of the 2026-11-14 line. That would be a design gap (the mark must be registered before the checkpoint that persists the advance), but it is a reading of the order, not a measurement: the three runs above did not hit the window. **What the next reading needs:** TAB-3b itself (`archive/tab3b.mjs`, W1 and W2, five runs, a conversation that already holds thousands of marks) rerun on a build after `ad2053fc0`, with `[CHECKPOINT]`/`stagePendingHistoryMarks` lines read in the first start's console to see whether a checkpoint lands between the decrypt and the mark. Two seats of this sitting (W6, W7) cannot replace W1 and W2: they hold a few hundred frames, not the thousands that make the window wide.
