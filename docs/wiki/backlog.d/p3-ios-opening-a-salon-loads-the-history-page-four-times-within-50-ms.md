## P3 - perf: iOS opening a salon loads the history page 4 times within 50 ms (S17, 2026-11-20)

target: 1.8.3

_2026-11-22: moved to 1.8.0 when 1.7.3 shipped._

Read on the iPhone 12, sitting S17 of 2026-11-20: opening a salon requests the same history page four times within 50 ms. Several openers each start the load with nothing coalescing them. Name the overlap and delete it, so one open is one load (a ledger that reconciles afterwards is a witness, never the fix). Verify by counting history requests for one open, on both phones and the web. Context: [history-reconciliation](../protocols/history-reconciliation.md).

**Read of the code, 2026-11-25 (not closed: the four openers are not named by the S17 log).** The coalescing already exists: `loadChannelHistory` (`useConversations.svelte.ts`) returns on a fresh `channelHistoryLoadedAt` entry and JOINS a load in flight when nothing was declared stale after that load's request left (`running.sentAt === salonStaleDeclarations`). Eight call sites start a salon load (the press at `MainChatPage` `atTap`, the selection effect, `openConversationFromId`, the listing's end through `reloadChannelHistory`, the live-stream transition, `ChatBackgroundService` at two places, and the generic `loadHistoryForConversation`). So four requests inside 50 ms means either four loads each declared stale after the previous one's request left (`invalidateChannelHistoryCache` is called from ten places, and bumps the counter even for another salon), or one load plus the `listReadMarks`/`listMessages` pairs of the others being counted together. Which one cannot be decided from the code alone: the next iPhone reading must carry the request log for ONE open (the `[CHANNEL] history load ... joins the one in flight` lines are present or absent). **Done on 2026-11-25:** the stale counter is per salon (`staleDeclarationsOf`; the every-salon declarations plus the salon's own), so a declaration for ANOTHER salon no longer makes a load of this one unjoinable; `useConversations.channelCache.svelte.test.ts` pins both sides. **Owed:** the iPhone reading that counts the history requests of one open (target `1.8.3`): if it still shows more than one, the log names the opener that declared the salon stale, and that opener is the next fix.

**2026-11-27 - re-read, and the log that will decide it.** No opener passes `force`, and none of the call sites declares the salon stale on an OPEN (the ten `invalidateChannelHistoryCache` callers are removals, edits, deletions, the prune, the Graine repair listener and the stream transitions), so four requests need THREE declarations landing between four request departures: the code cannot produce that from one open alone, and no redesign was made on a guess (a trailing single-flight would change the pinned "a stale declaration after the request left is asked again at once" rule for nothing measured). What was added is the missing evidence: every declaration now logs (`history of <salon> declared stale (n load(s) in flight)`) and every load that STARTS logs why it did not join (`history load of <salon> starts (generation, forced / at the tap / not forced, none in flight / the one in flight is not joined)`). **Owed (reading, target `1.8.3`):** open ONE salon on the iPhone 12 from a cold list and read those lines in the app log: N `starts` lines with M `declared stale` lines between them name the declarer's neighbours; zero declarations between four `starts` would mean the join is broken and is the next fix.
