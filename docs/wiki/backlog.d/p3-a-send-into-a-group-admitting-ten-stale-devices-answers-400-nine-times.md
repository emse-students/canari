## A send into a group that admits ten of alpha's devices answered `400` nine times on `/api/mls/send`

target: 1.7.0

**Seen 2026-11-15** on dev (`1.6.12-alpha.2`) by `bun archive/notif17b.mjs` (rig log kept out of the repository): beta's web seat minted a group, added alpha, and logged `POST /api/mls/send -> 400` nine times in the minute that followed, around `[COMMIT] ... admits 10 device(s) at epoch 2` (alpha has ten enrolled devices, most of them stale rig devices) and `[HISTORY_BUNDLE] ... cannot be addressed ... pushing it nothing`. The group still worked (the push, the conversation on the phone), so the `400`s are noise upstream of something: a send addressed to a device that cannot take it, or a duplicate. **To do:** read the response body and the request kind of those nine sends (Welcome per device? a duplicate commit?) on a dev run with the network tab open, then either make the sender skip what it knows will be refused or name the expected refusal and stop logging it; a stale device that stays on the roster for ever is a second question (device lifecycle). Per the repository's noise rule it is not to be demoted.

### What the nine `400`s are (read 2026-11-15, `1.6.12-alpha.2` on dev, the beta seat's network captured through CDP)

One `bun archive/notif17b.mjs` run with a second CDP client recording `Network` on the beta seat (request SHAPE and response body only, no ciphertext kept). **Nine `POST /api/mls/send` answered `400`, every one with the same body: `{"error":"addressed_unsupported","message":"the addressed device(s) did not declare addressed-history-1","devices":[<one device>]}`.** Nothing else on `/api/mls/` answered an error.

- **Request kind of all nine: an ADDRESSED, transport-only history answer** - `silent: true`, `durable: false`, `recipientDevices` of exactly ONE device. Not a Welcome (a different frame), not a commit (the commit is the `silent: false, durable: true`, no-recipients frame that answered `201` right after each admission), not an application message (the chat message, same shape as the commit, answered `201`). Each `400` is followed in the console, within 100 ms, by `[HISTORY_BUNDLE] <device> cannot be addressed ... pushing it nothing` / `answering nothing rather than broadcasting`: the sender LEARNS the refusal from the `400`.
- **Where they come from.** `[COMMIT] ... admits 1 device(s) at epoch 1` (the one device admitted at epoch 1 is a second, stale web device of beta's own account) produced the first `400`; `[COMMIT] ... admits 10 device(s) at epoch 2` (alpha's ten enrolled devices) produced eight more. The other two of alpha's ten, the phone and one live web device, were answered `201` (an empty bundle, and a one-message bundle): the answer path works, the `400`s are the devices that cannot take it.
- **Why the server refuses.** `apps/chat-delivery-service/src/services/messaging.service.ts` (`addressed_unsupported`): an addressed transport frame is accepted only for a device that is ONLINE and every live session of which declared `addressed-history-1`. The refused devices are enrolled rig devices that are not connected (the entry's own "stale"), so they are refused for being offline, not for an old build; the body does not say which (the server log line does: `per device: ...`).
- **Likely cause.** The sender (`groupActions.ts`, `sendStateOnly` and the bundle chunks) addresses ONE answer to EVERY device of the admitted set that the commit lists, without asking whether the device is reachable; the server is the only party that knows presence, so the answer is found by failing, once per stale device. The roster of ten is the second question already named above (a device that never signs in again stays enrolled). The group works because the live devices were served.
- **Not fixed here.** Candidate directions for the fix, both within the "never learn by failing" rule: carry the addressability from where it is known (a presence/capability read for the admitted devices before the sends), or let the server answer the batch in one call naming the unaddressable devices as an expected outcome and stop logging it as an HTTP failure. Evidence: rig-local capture, kept out of the repository.
