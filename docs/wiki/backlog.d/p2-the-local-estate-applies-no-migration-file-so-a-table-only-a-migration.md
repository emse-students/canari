## P2 - the local estate applies no migration file, so a table only a migration creates is missing (2026-10-22)

target: 1.8.4

The local estate's schema comes from TypeORM `synchronize`, and nothing runs `apps/*/src/migrations/*.sql` there. A raw-SQL table therefore never exists locally. On 2026-10-22, every salon send failed with `relation "channel_message_client_tombstones" does not exist` (migration 090), and `post_audiences` (071) was missing too. GRAINE-AUTH-1 read this as `never appeared`. Both files were applied by hand that day. The fix is for the local bring-up to call `apply_migrations` from `infrastructure/lib/migrations.sh`, as the deploy and the dev reset already do.

**Re-read 2026-11-25: the fix as written collides with the owner's hold, so it is not the one-line call it looks like.** A local database has no `schema_migrations` ledger, so `apply_migrations` sees all 262 files as unrecorded, and `require_owner_approvals` examines every one: measured on `main` that day, **27 historic files are held and not approved** (the `DROP`s of 052-056, 072, and the rest; 17 more are approved), so the loop refuses before applying anything - by design, it is the guard production relies on. And no reading exists of the plain files replayed against a schema `synchronize` built from today's entities (an `ADD COLUMN` without `IF NOT EXISTS` would fail there). What would close it, to be decided before it is built: either the local bring-up seeds its ledger from a fact (the files whose objects the ORM schema already carries) and then runs the loop, or the local estate applies only the files that create what no entity declares. Either needs one measured replay on a `make run-services` database first. Still `1.9.0`.
