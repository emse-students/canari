## [v0.12.0] - 2026-08-03

### Added
- **WP-POST-DOC-2: a PDF attachment shows its first page instead of a generic icon.** Rendered client-side with pdf.js onto a canvas, which is the only option available and not a preference: chat and post media are encrypted with a per-file CEK before upload, so the backend holds an opaque blob and cannot rasterise anything, and an `<iframe>` on the decrypted blob would render on desktop and iOS but not on Android, whose WebView has no PDF engine at all. pdf.js and its worker are behind a dynamic `import()`, so nothing is fetched until a PDF is actually displayed and the worker stays a separate chunk. A post renders the page full-width under the file row - the surface is wide, and that space is exactly what used to be empty - while a chat bubble puts it in the 44 px icon square, so each surface rasterises the document once, at the size it can afford. The preview is strictly a bonus: an unreadable, password-protected or oversized PDF keeps the icon and, above all, keeps its download button. Deliberately excluded, with a reason rather than an omission: the conversation media panel and the association document vault list files without fetching them, so previewing would mean eagerly downloading and decrypting every document in the list to draw a thumbnail - and for a password-protected vault document it is not merely expensive but impossible, the CEK being derived from a password the server never sees and the viewer has not typed

- **WP-AGENDA-1: an event can be edited and deleted from the global agenda.** The buttons existed only inside the owning association, so touching an event meant first working out which association had filed it - and for a BDE validator, who may edit any association's event but holds `PROPOSE_EVENT` in none of them, that page never offered the buttons at all. The detail modal already accepted `canEdit`/`onEdit`/`onDelete`; the global agenda simply never passed them. It does now, gated per event on the same rule the server enforces on `PATCH`/`DELETE /associations/:id/events/:eventId` - a global admin or a BDE `VALIDATE_EVENTS` holder may touch any event, anyone else needs `PROPOSE_EVENT` in the association that owns it - so the surface grants nothing the API would refuse. Editing reuses the deposit modal in a second mode: the owning association is shown read-only rather than as a picker, because an event does not change owner, and `kind`, the linked form and the poster are deliberately left out, being editable only from the association's own page where an omitted field is left unchanged server-side. The modal's association line no longer disappears when the buttons appear: it was suppressed on `canEdit`, which is right on an association's own page and wrong on the global agenda, where the name is the context - the two are now separate props, and co-owners are listed either way since they are never redundant

### Fixed
- **A favicon appeared, then was replaced by the globe a moment later.** The candidate chain was walked by cascading the displayed `<img>` through its own `onerror`, and that is one element reused across every candidate: assigning a new `src` aborts the previous load but does not unqueue an error already fired for it, so the stale event advanced the pointer past the candidate now on screen. The chain is rebuilt the instant the preview payload arrives carrying the site's declared icon - which is exactly when a conventional path tried meanwhile is in flight - so the sequence was reliably: try `/favicon.ico`, get the preview, display the real declared icon, receive the `.ico` failure, walk past the icon being displayed, run out of candidates, globe. `sky.mitv.fr` hit it every time. Candidates are now probed with their own off-screen `Image`, so an answer can only ever be about the URL that was asked, and the `<img>` renders a winner already proven to decode. It also fixes the silent half of the same bug: a server answering `index.html` with a 200 for `/favicon.ico` produces bytes that are not an image, which the probe rejects like a 404. The globe waits for a verdict rather than standing in during the search
- **A link preview printed the same sentence twice.** The amber chip above the title showed `og:site_name`, and a great many sites - personal ones especially - set that tag to the page title, so the card read "HI, I'M ALEX KATES" over "Hi, I'm Alex Kates". The chip now carries the hostname instead, which is short by construction, cannot repeat the title, and is the one thing the title does not already say: where the link actually goes. It also stops being uppercased for an external link, a hostname not being a label. Nothing changed for an in-app link, whose chip names a kind of content ("Publication", "Association") rather than a site
- **Every MLS system event was rendered as its own raw JSON, and the event it carried was never applied.** A community invitation arrived in the DM as a wall of `{"channelId":"...","inviterName":"..."}` instead of a card with a Join button, and the key distribution that travels with it appeared as a second blob - so what looked like two cosmetic glitches was one control message that was displayed instead of executed. `appMsgToEnvelope` had been given a `msg.system` branch in an unrelated commit (`7e9d66e8`), and its whole contract is that it returns null for anything that is not displayable: both replay paths - the Welcome buffer in `setupMessageHandler` and the history replay in `history.ts` - are written as `if (envelope) { display } else if (parsed.system) { handle }`, so the moment it stopped returning null, `handleSystemEvent` and `applyReplaySystemEvent` became dead code. That branch is removed and the contract restored, with a test pinning it. The same fault explains the community notices ("X a ajoute Y au groupe") appearing left-aligned under a sender's name and avatar: a channel really does transport its notices as an already-localized sentence, which is why the branch had been added, but the two channel decode sites now ask for it explicitly through `appMsgToChannelSystemEnvelope` and attribute it to `system` rather than to whoever triggered it, so it renders centred and neutral like every other notice. An invitation that lands while the device is offline now also replays into a card, and all three producers of that card - the inviter's local insert, the live event on their other devices, the replay - derive one id from the invitation itself (`channelInviteMessageId`), so they converge on a single bubble instead of stacking three
- **An image received while the tab had been open a while only appeared after a reload.** The access token lives in memory for minutes and refreshes itself silently, but the copy the chat session hands down its component tree is captured once, at login, and never updated. Media already fetched kept displaying (its ciphertext is in the Cache API), so nothing looked broken until a NEW image arrived and its download 401'd with a token that had expired hours ago - and a reload, which mints a fresh one, "fixed" it. The token is no longer passed to the download at all: `mediaBlobCache` resolves it per request through `getToken`, which refreshes when it is within a minute of expiring. The `authToken` prop stays where it is, but only as what it always really was - a signal that the session is authenticated
- **The members panel showed the whole community in a private channel.** `listChannelMembers` returned every workspace member regardless of the channel, so a channel restricted to admins listed all nine people who could not read it. It now answers the channel's own roster - its explicit `allowedUsers` plus anyone holding `workspace.manage`, exactly the rule `canAccessChannel` enforces, resolved from the roles already loaded rather than one query per member - and refuses the roster of a private channel to a member who has no access to it. The settings panel asks for `?scope=workspace` instead: the picker that grants access to a private channel has to be able to offer people who are not in it yet
- **"Modifie a" ran into the time in the message info tooltip.** Svelte trims whitespace at a block boundary, so the space before an `{#if}` opened on the same line as the label was dropped
- **No link preview worked in production at all, and nothing said so.** Every card fell back to the URL as its title and a globe for its icon - reported as a missing favicon, which is what it looks like from the outside. The endpoint was answering `400 Link preview failed` for github.com, example.com, canari-emse.fr and sky.mitv.fr alike; only YouTube links survived, and that is the clue, because YouTube goes out through the oEmbed path and every other link goes through the one fetch that carries `dispatcher: ssrfSafeDispatcher`. That dispatcher is an `Agent` from the `undici` package, handed to Node's *global* `fetch`, which is backed by the undici Node bundles itself. The two copies no longer agree on the dispatch handler interface, so the request died at `InvalidArgumentError: invalid onRequestStart method` before a socket was opened - which also means the SSRF connect-time guard has not run once since the undici major bump, not because it was bypassed but because nothing ever got as far as it. The call now goes through `ssrfSafeFetch`, which pairs the dispatcher with undici's own `fetch` in one place, so no call site can separate them again; `url-guard.spec.ts` pins the pairing offline by requiring a fetch to `localhost` to fail with `ESSRFBLOCKED` - our lookup ran - and with nothing else. What made a total outage invisible is worth naming separately: `fetch` reports any transport failure as a bare `TypeError: fetch failed` with the real reason in `cause`, and the handler caught it and answered a generic `Link preview failed` without logging, so a runtime rejecting our dispatcher was indistinguishable from a site refusing us. It now logs `[LINK_PREVIEW] <host> failed: <cause>`
- **A favicon that 404s fell straight through to the globe.** The client had one candidate - the icon the preview declared, or `/favicon.ico` when the preview itself failed - and a single `onerror` retired the icon for good. One missing file is not evidence that a site has no icon: `sky.mitv.fr` serves an SPA that answers `index.html` on `/favicon.ico`, a 200 that is not an image, while its real icon (`sky.png`) is declared in the page and perfectly loadable. `faviconCandidates` now builds an ordered list - the declared icon first, in whatever format the site chose, then `/favicon.ico`, `/favicon.svg`, `/favicon.png`, `/apple-touch-icon.png` on the origin - and the card walks it on each failure, so the globe is what is left once every candidate has failed rather than a shortcut taken at the first one. The scheme check stays on the client too: the declared icon comes from someone else's markup and lands in an `<img src>`
- **The personal notepad was stored in clear in the database.** The profile notepad is offered as private, and users treat it as such - a password jotted down, a note about someone - but `users.notes` held the markdown verbatim, so anyone reading the database read the notepad. The association notepad had been encrypted since it was built (`notesCiphertext`, AES-256-GCM under the association's vault key); the personal one had simply never been given the same treatment, and its own source comment said so. It now uses that exact envelope - `encryptVaultNote`/`decryptVaultNote` are shared rather than copied - under a per-user key generated on first use, stored in `users.notesKey` and served only to its owner. This is deliberately not zero-knowledge, and the alternative was weighed rather than overlooked: deriving the key from the PIN would put it beyond the server, but the PIN is absent on the biometric path and the existing "forgot PIN" escape hatch wipes MLS state - notes would become permanently unreadable, turning a privacy improvement into a data-loss trap. The threat addressed is a readable database, not a hostile operator. The old plaintext is not dropped by the migration, because only the client can encrypt it: the server returns it once as `legacyNotes` while no ciphertext exists, the client re-saves it encrypted, and that save nulls the column - a reader for the previous format shipping in the same commit, and a conversion that runs itself
- **A link preview showed a generic globe for any site Google has not indexed.** The favicon was fetched from `google.com/s2/favicons`, a service that only knows hosts it has crawled and answers a placeholder icon for everything else - indistinguishable, to the caller, from a site whose real icon happens to be a globe. Every self-hosted or unlisted site therefore looked iconless, `sky.mitv.fr` among them. The icon now comes from the site itself: the preview endpoint already downloads the page to read its Open Graph tags, so it also resolves `<link rel="icon">` from that same document - preferring the largest declared `sizes`, then an `apple-touch-icon`, over a 16 px `.ico` - and falls back to the conventional `/favicon.ico` on the origin, which is what a browser requests anyway. The client no longer contacts Google at all, which also stops handing a third party the hostname of every link opened inside an end-to-end encrypted conversation, and an icon that 404s now degrades to a globe glyph rather than a broken-image marker. The `href` is attacker-controlled markup that ends up in an `<img src>`, and writing the test for it showed that `new URL()` resolves rather than rejects a hostile value - `javascript:` and `data:` survive as absolute URLs - so the scheme is checked explicitly instead of relying on a parse failure that never comes
- **WP-POST-DOC-1: a document attached to a post was drawn at the top of a large empty box, and in a gallery it shifted every image's lightbox.** The post attachment container reserves space with `aspect-ratio` while the media decrypts, which is right for a picture - the box stops the feed jumping when the image lands - and meaningless for a document, whose card sizes itself. A PDF carries no `width`/`height`, so the fallback 4:3 ratio applied: a 70 px file card stranded at the top of a ~430 px plate, which is the reported symptom. The reservation is now a decision, `reservesAspectRatio`, taken per resolved media type at the three sites that reserve - a post's single attachment, a gallery cell, a comment's attachment - rather than unconditionally. `PostMedia`'s own placeholders followed the same rule and had to move with it: the file skeleton and the error box were positioned `absolute inset-0`, which only renders inside a parent that has a height of its own, so removing the ratio would have made a decrypting document invisible and, worse, made a document that FAILED to decrypt invisible too - the one state the user must see. Both now take part in the flow when nothing was reserved, and the skeleton mirrors the loaded card's footprint so nothing jumps on arrival. The gallery bug is the second-order one and was not visible in the report: `lightboxMedia` is `postMedia` filtered to image and video, but each cell opened the lightbox at its index in the FULL array, so a single document among the attachments renumbered every image after it - clicking one image opened the next, and the last one opened nothing at all. A cell now resolves its own index in the lightbox array, which is also the flag for "not lightboxable" (`-1`), so the position and the affordance can no longer disagree. Three copies of the type-from-mime fallback collapsed into one `resolveMediaType`. Also: the file size sat under a `uppercase` class, rendering "148.8 Ko" as "148.8 KO"
- **WP-HIST-2: a device that rotated its MLS identity asked every conversation for history it already had, forever.** The pending-history banner sat over conversations that displayed all their messages, and the log showed the same three groups re-solicited on every connection, session after session, each attempt answered `NO_PEER_ONLINE` by the delivery service. The banner was not lying and the retry ladder was not looping: the diagnosis behind them was simply wrong, and nothing could ever revisit it. Soliciting was triggered by an EVENT - "I joined this group" - and cleared by another - "a bundle arrived". No inventory anywhere. That reading is false for the commonest join of all: the message store and the seen-frame ledger are keyed by USER, not by device, so a device rotating its MLS identity inside the same browser keeps every message while its new identity is a member of nothing. Recovery then external-joins each group in turn and, on the old rule, marked every one of them as awaiting history - the whole account, in one pass, durably, with only a bundle that nobody needs able to clear it. Both join paths now go through one decision seam, `solicitHistoryIfMissing`, which asks only when the device can point at something missing: an existing marker (a gap the replay PROVED), or an empty local store for that group (holding nothing, we cannot tell an empty conversation from a missing one - and this is the sole case covering a group whose server-side stream was trimmed, a gap no replay can ever observe, since a frame that is gone never fails to decrypt). A failed store read falls through to asking, a failed read proving nothing either way. The evidence itself comes from where the app already knew it and threw it away: the replay classifies every decrypt failure, and the branch that declares a frame permanently undecryptable - retries exhausted, pre-join or forked epoch, obtainable only re-encrypted from a member - is the one moment "history is genuinely missing" is established. It now records it, which it must do there or never: the frame is consumed in the same breath and will never fail again to remind us. Markers consequently carry their reason (`no-local-history` / `unreadable-frames`, a proof never downgraded to a presumption), and one written without a reason is legacy - posted blind by the old behaviour - so it is dropped rather than replayed, which is also the one-shot migration that clears the markers already sitting in every affected browser. Not changed, deliberately: the delivery service already answers `no_peer_online` synchronously and the client still ignores that answer, opening a 30 s window and burning a retry for a question already settled. With the marking fixed the request is no longer made at all in this case, and the manifest-based exchange planned next replaces that path wholesale
- **WP-INT-1: the Cercle cotisant-status endpoint was closed in production, and the deploy could not have opened it.** `GET /api/public/cotisant-status` is what Le Cercle calls before letting a member drink, and it is gated on `CERCLE_API_KEY`. That key had never been generated: production carried an empty value, and `assertCercleApiKey` compares timing-safely against the expected string, so an empty expected value never matches - every request was rejected. Not a degraded mode with a sensible default, a closed door, and one that only shows up as the bar losing cotisant status for no visible reason. The variable was also absent from `cd.yml` entirely while being present in both compose files and in `.env.example`, so the CD - which regenerates `infrastructure/.env` from the repo secrets on every deploy - would have written the empty template value back over any hand-edit made over SSH. That is the half worth naming: setting it on the host was not a shortcut to skip the pipeline work, it was a fix with a deploy-shaped expiry date. The key is now a GitHub secret, synced next to `EXTERNAL_API_KEY`/`SKY_API_KEY` and warning when unset, in the same shape as every other optional credential. The runbook told the operator to edit the host file and "also set it as a GitHub secret if the deployment pipeline injects it" - it now names the secret as the source of truth, gives the deploy step, and gives a check that reports whether the key is populated without printing it
- **WP-PDF-1: the right half of a co-owned event's watermark painted nothing, and the calendar grid never split at all.** The split markup was correct, the logos resolved, the rasteriser was faithful and the fix was deployed - the defect was a global stylesheet rule none of it accounted for. This markup renders inside the app document (the preview inline, the export in an offscreen container), so Tailwind Preflight's `img { max-width: 100% }` applies to it, and a band image declaring `width:<circle>px` inside a window half that wide was clamped to the window. Measured on production: an image whose inline style said `25px` rendered at `12.5px`. The first band survives - squeezed to a centre strip of its own logo, which still looks like half a logo - while the second, offset by `left:-12.5px` with only 12.5px of width left, is pushed entirely outside its own window and paints nothing. Left half present, right half gone, exactly as reported, and the surviving strip is what made it read as a half-working split rather than a broken one. The band image now carries `max-width:none;max-height:none`. What made this expensive is that it is invisible outside the app: a standalone probe page has no Preflight, so the markup, the geometry, the real production data, snapdom's rasterisation and the deployed bundle each verified as correct in isolation while production stayed broken - four dead ends before measuring the live DOM, where the computed width contradicted the inline one. Separately, the on-screen calendar grid was never part of the split work at all: it still drew a row of small whole logos side by side, the design that was explicitly rejected, because only the export was fixed. Both surfaces now read one `splitLogoBands` geometry, so the split is defined once and cannot drift again. The grid's single-owner watermark was a rounded rectangle for the same reason the split would have been an ellipse: `width:62%;height:62%` resolves the two percentages against different axes, so the box was only ever square by accident, and on the usual slot - wider than it is tall - it drew a squashed pill. It is now sized off the slot height alone with `aspect-ratio:1`, matching the export's `slotH * 0.62` square exactly (25px for a 41px slot, measured), so both surfaces draw the same circle whether the event has one owner or several The landing ended itself at the instant it succeeded. A deep link publishes the MLS **group id** to `notifNav` and the landing holds that target until the conversation is actually displayed - deliberately, because the conversations map is emptied and rebuilt wholesale by the IndexedDB restore, so a target selected while the map is still filling is dropped moments later and the hold is what re-asserts it. But a conversation is keyed by its **display name**: `openConversationFromId` finds a DM by scanning for `conversation.id === target` and then selects it by that key, and `selectConversation` calls `endLandingUnlessTarget(key)`, which compared the key it was given against the pending group id. Different strings for every DM and every group - equal only for a community channel, which is keyed by the very id that names it - so the landing read its own selection as the user opening something else and released the target. The restore then dropped the selection with nothing left to re-assert it, which is exactly the reported symptom, and it is why channels behaved and DMs did not. The same raw comparison sat in the landing's idle guard (`selectedContact === id`), where it had the mirror-image effect: a landed DM never looked landed, so every mutation of the conversations map re-selected it and re-requested its history. Both now go through one `resolveConversationKey` - the single id -> key lookup that `openConversationFromId` is itself now built on, rather than a third copy of the scan - so there is one place where a target becomes a key and one thing to get right. Pure frontend; the native chain is untouched. A tapped deep link also logs `[notifNav] deep link received: <url> -> target <id>` before anything else runs: the tap crosses a PendingIntent, `onNewIntent`, the Tauri deep-link plugin and `hooks.client.ts` before reaching any of this, and until now failed silently and indistinguishably at all four - which is how this check came to be recorded as passing while it was broken
- **WP-PDF-1: a co-owner without a logo renumbered the watermark bands, and the weekday labels sat too high.** Two unrelated defects in the same export. The split watermark is intentional - one circle, the left half cut from the first owner's logo and the right half from the second - and the resolved logos were compacted before being handed to the composer, so an owner whose logo did not resolve did not leave a gap, it renumbered the bands: two owners with one usable logo collapsed to one, and the survivor was drawn WHOLE across the circle, which is very hard to tell apart from a working split. A band now belongs to an owner, positionally, and an unresolved logo simply leaves that owner's half empty - the symptom is legible instead of disguised as a correct render of different data. Each missing logo also names its association and its event in the console, distinguishing an association with no logo set (the export is then correct and the request is a different feature) from one whose logo could not be inlined. **This is not what the original report described**, and saying so is the point: re-rendering the production markup with the real production data showed both halves painted, every logo resolving, and every logo fully opaque - the right half is drawn and cannot be seen, because each half is composited at a fixed 0.20 opacity over its OWN owner's brand colour and a logo tends to be in its brand's colour family. Measured against the real bands, the shift ranges from +29 luminance to **-4** (a black logo on a black brand colour: mathematically invisible). The shift is linear in opacity, so the remedy is per-half adaptive opacity; it is not applied here. Separately, the weekday labels were centred in the preview and too high in the exported PDF: the export re-draws every `data-pdf-text` run as real vector text anchored to the TOP of the marked element, and the marker sat on a container with 11 px of vertical padding, which the re-draw knows nothing about. The marker moved to the inner span - whose box is the text's own line box - and the cell centres it with flex, which also makes the row height explicit rather than padding-derived, matching the value the cell-height arithmetic already assumed. The renderer now states that markup contract in its docblock, since nothing about the marker communicates it and the failure is invisible until the two views are compared side by side
- **WP-DEV-PANEL-1: a deleted device that came back was registered, invisible and mute, forever.** Deleting a device denylists its id permanently, and `resolveDeviceId` deliberately hands back the *same* id after a reinstall - it reads `localStorage`, then `push_context.json`, precisely so a reinstall does not churn the identity. Those two intentions met without ever having been introduced: `registerDevice` did not consult the denylist, so it wrote the KeyPackage and answered 200, while `getUserDevices` filtered the device out of its own list and `resolveKeyPackagePayloadForDevice` resolved it to `null`. The device believed it was enrolled, never appeared in its own device panel, and could no longer be a target for any Welcome - so it silently received nothing from any new group, with no error raised on either side. That is the cause behind the panel symptom the previous release could only guard against. Registration now refuses a revoked id with `403 { code: 'DEVICE_REVOKED' }` and logs it, which is what makes a revocation mean anything: the comment at the deletion site promised to "prevent immediate re-registration", but nothing expired the row and nothing enforced it either. The client answers by becoming a new device - `generateKeyPackage` catches the typed `DeviceRevokedError` (typed, because branching on an error message is how this class of bug survives a refactor) and rotates the identity: fresh id, empty MLS state persisted *before* anything else may fail, abandoned id deregistered. Retried exactly once; a second refusal is a server bug, not a state to keep rotating through. The MLS credential is `userId:deviceId`, so a new id *is* a new device: local history is gone and every group re-invites it, which is the intended cost of a revocation being real rather than a silent half-state. The rotation itself is not new code - it is the block the credential-mismatch path already ran, in two near-identical copies that differed only in how each platform persists a snapshot; both now call one `rotateDeviceIdentity`, with the persistence difference behind a `persistFreshState` hook
- **WP-NOTIF-1: an undelivered notification quick reply was silently dropped.** A reply typed from the shade is built natively and appended to `outbox_pending.ndjson`; when the background drain could not deliver it, that file was the only place it existed. `store_outbox_mirror` rewrites the mirror from the TypeScript queue, which has never heard of that entry - so the next foreground outbox mutation erased it rather than flushing it, and the reply was gone with no trace anywhere. The mirror is now read as well as written: at login, `adoptOrphanedMirrorEntries` turns every mirror line the TS outbox does not know about back into a real outbox entry, plus the local message the sender never got, and the ordinary flusher owns it from there. It is the symmetric twin of `reconcileOutboxSent`, which only ever deleted. The adoption runs *before* conversations are loaded, so the adopted message is picked up by the ordinary history load and marked pending by `applyOutboxPendingStatuses` with no separate in-memory merge path to keep correct. The proto is decoded rather than replayed opaquely, so the entry becomes a first-class `text`/`reply` the flusher re-encodes identically (same messageId, same `sentAt`) - a silent entry stays `control`, sent verbatim and without a push, which is what silent means. A proto that is neither logs and is left alone: that branch is the bug being fixed, and it must not be the one thing that still loses a message quietly. A delivered send is removed from the mirror by the native drain, so an entry still present was not delivered; should one race through anyway, `reconcileOutboxSent` deletes it moments later, adoption being idempotent on the stable messageId. New Rust command `read_outbox_mirror`, which deliberately does not clear the file - the mirror stays authoritative for the background service until the next rewrite
- **WP-PDF-1: the agenda PDF had rounded corners and an uncropped background.** A sheet of paper is a rectangle, and the export container carried a 12 px radius that rasterises as four transparent notches at the page edge; it is gone, from the preview wrapper too, since the preview's job is to show the sheet that will print - a decorative radius belongs to the page chrome around it. The background image was an `<img>` with `object-fit: cover` inside a div that had a width but no height, patched in JS after insertion on the export path only: the preview never got one, so the image fell back to its intrinsic ratio, and neither view was reliably cropped - the sheet showed bands wherever the photo's aspect did not match A4. It is now a CSS background on a box pinned to the container (`inset: 0`), so `cover` crops against a box that always has the sheet's exact dimensions, in both views, with nothing left to patch afterwards; it also survives rasterisation more predictably than `object-fit` on an inline replaced element. The scrim became the image layer's sibling rather than its child, so the legibility overlay is no longer faded along with the photo it exists to counteract. Logo fetch failures now log: a logo that cannot be inlined is simply absent from the PDF and the export still reports success, so nothing on screen distinguished a logo that failed to fetch from one that was never set
- **WP-DEV-PANEL-1: the device panel could be emptied down to "0 devices connected" without objecting.** On Windows the current device was not highlighted, and every row - including the machine in use - could be deleted. The panel's code was not the defect: it highlights `myDeviceId`, badges it, and hides its delete button. Every one of those safeguards is keyed on matching our id against a row the server returned, so when no row matches they do not fail, they simply do not appear, and the panel degrades into a list of other people's machines with nothing marking it as wrong. That matters more than a missing highlight because the deletion is not recoverable by logging back in: `deleteDevice` purges the device's memberships, KeyPackages, prekeys, push token and queued messages, then denylists it against re-registration. Two changes, both on the client. A deletion that would leave the account with no device is now refused outright with an explanation - reaching zero can only mean we failed to recognise ourselves, so the row about to be deleted is the machine in use. And when the current device is absent from its own list, the panel says so, naming the id it looked for, instead of rendering a list that looks normal; it also logs it, because the cause is server-side (the list is filtered to the 90-day retention window and excludes denylisted devices, and a device whose KeyPackage cannot be resolved is dropped) and is not diagnosable from what the UI shows. The error banner also moved above the list rather than replacing it, so a refused deletion is read next to the devices it declined to touch
- **WP-EDIT-1: editing a message did not save it, and neither did deleting one.** Edit a message, reload, and the old body was back. The edit itself was fine - `editMessage` captures an `edit_message` control event in the durable outbox and peers apply it correctly - what was missing is that nothing wrote it down on the device that made it. A sender never receives an MLS echo of their own message, so `systemMessageHandler`, which is what persists an edit on every *other* device, never runs on ours; `handleEditMessage` applied the new body to the in-memory conversation and stopped there, so the next load read the pre-edit row straight back out of the encrypted store. `handleDeleteMessage` had exactly the same hole and was one reload away from the same report. Both now persist through a single `persistLocalMutation`, which `handleAddReaction` - the one mutation that did persist, inline - was also folded into, so there is one place where a locally-applied mutation is written and one thing to get right. It is best-effort and logs on failure, the control event being already durable in the outbox: a failed write costs a stale local row, never a lost mutation for the group. Two consequences of the same root cause are fixed with it. `editedAt` existed on the in-memory message and on neither `StoredMessage` nor the at-rest payload, so even on a peer - where the edit *was* persisted - the edit time was dropped at the next load and the info tooltip showed "modified at" with nothing after it; it is now stored, and the two paths that rewrite a row without re-reading the event (a history replay, the post-replay mutation pass) preserve it, as they already did for the edited body. And since the two storage backends duplicated that projection - each with its own copy of the payload build and three copies of the decode - which is precisely how a field gets added to the type and to neither writer, both now share `toMessagePayload`/`fromMessagePayload`, tested for the round trip including a row written before `editedAt` existed. Web and desktop; no native or backend change
- **A reply sent from a notification left no trace on the device that sent it.** The quick reply does work - the log shows the proto built, queued and POSTed, `HTTP 201`, `1 sent, 0 remaining` - but it is built and delivered entirely natively and never becomes a TypeScript outbox entry, and `reconcileOutboxSent` only *deletes* entries. So the peers received the message and the sender's own conversation showed nothing, which from the app is indistinguishable from a reply that was never sent; the notification was then cancelled, removing the last evidence it had happened. A delivered reply is now written to `fcm_message_cache.ndjson` - the same cross-process file an incoming push already uses - under OUR user id, which is all the injection path needs: `mapStoredMessagesToChatMessages` derives `isOwn` from `senderId`, so the row renders as our own message and raises no phantom unread. It is written before the notification is cancelled, so the visible trace is never dropped before the durable one exists, and only when the drain reports 0 remaining: an undelivered reply must not appear as sent. Both platforms, since both had the defect - `writeSentMessageToCache` (Android) and `CanariWriteSentMessageToCache` (iOS), each factored out of its platform's existing cache writer rather than duplicating the bounded append. One asymmetry is left standing and documented: an undelivered reply lives only in `outbox_pending.ndjson`, which `store_outbox_mirror` rewrites from the TypeScript queue, so the next foreground outbox mutation wipes it instead of flushing it - the notification is deliberately left up as the retry affordance
- **Our own avatar was blank in the notification thread.** `MessagingStyle` takes two `Person`s and only the sender's carried an icon; Android attributes the inline reply to the self `Person` while it is in flight, so the one message in that thread the user actually wrote showed a blank face. It now carries our avatar, through the same 24 h file cache as the sender's, so it costs at most one request a day and an unresolvable avatar simply stays iconless. Our id comes from a new `MlsContextLoader.loadUserId`, which reads just the `userId` field of `push_context.json` - deliberately not `loadPushContext`, whose expensive half is a Keystore round trip this caller has no use for. Android only: iOS shows a single attachment image rather than a thread, so it has no self `Person`
- **Every chat open issued a `GET /api/users/system` that could only 404.** The chat gives its own system messages the sentinel senderId `system`, and the display-name resolver treated it as a user id: one request per open, a 404, and a two-minute failure-backoff entry for a name that does not exist. `resolveUserDisplayName` now recognises the sentinel and answers `null` without a request - null rather than the "unknown user" label, because system-message text is stored and a label baked into it would outlive the cache miss
- **A brand-new conversation asked for its history forever.** Joining a group solicits a `history_bundle`, because a joiner lands at the current epoch and cannot tell a group with no history from one whose history it simply cannot decrypt - so a conversation created seconds ago solicits exactly like one with years behind it. The responder, `sendFullHistoryBundle`, returned silently when its local store held no message for that group, and silence is also what a killed or backgrounded responder produces. The requester could not tell them apart: every join of a fresh conversation ran the full 30 s window into `pending-offline`, showed the offline banner, and kept its durable awaiting-history marker - re-soliciting on every reconnect for the 30 days of the give-up horizon, for history that does not exist. An empty group is now answered with a `history_bundle` carrying `messages: []`, which closes the loop at no cost: the receiver calls `noteHistoryBundleReceived` before it even reads `messages`, so the empty bundle clears the pending window and the durable marker alike. The answer is only sent when our emptiness is authoritative, which is the whole difficulty - the server picks ONE random online member, and a member that just joined has an empty store for a group that may hold years of history held by others, so answering "empty" there would wrongly close the requester's loop for good. A responder still awaiting that group's own history (`isAwaitingHistory`, same registry and same horizon) stays silent, and so does one whose local read threw, a failed read proving nothing either; in both cases the requester retries and the server rotates to another member. Silence still means "ask someone else", only an explicit empty bundle means "there is nothing". The two silent branches now also log, per the outbox rule that a swallowed branch leaves nothing else behind

### Security
- **The link-preview SSRF guard could be walked past three ways.** `/api/mls/link-preview` fetches a user-supplied URL from inside the cluster, and `isPrivateIpAddress` is the whole decision - it is consulted both before the fetch and again at connect time by the undici dispatcher, so an address it calls public is one the socket reaches. It called three families of address public. `0.0.0.0` was not in the IPv4 list at all, and under Linux a connection to `0.0.0.0` lands on loopback, so `http://0.0.0.0:8080/` reached any service bound to the wildcard address; `::` was the same hole on IPv6. Worse, the IPv6 branch only recognised `::1`, `fc`/`fd` and the literal `fe80:` prefix, so every IPv4-mapped form was waved through: `::ffff:127.0.0.1` and its hex spelling `::ffff:7f00:1` are addresses whose socket lands on loopback, and Node's resolver hands back exactly that shape - both barriers judged them public. And because `URL.hostname` keeps the brackets around an IPv6 literal, `isIP('[::1]')` answered "not an address" and the literal check was skipped entirely, leaving only the DNS path to catch it by accident. The predicate is now split per family and widened to the blocks a server-side fetch has no business reaching - `0.0.0.0/8`, CGNAT, the protocol and benchmarking assignments, multicast and reserved space on IPv4; the unspecified address, the full `fe80::/10` rather than one hextet of it, and multicast on IPv6 - while any address embedding an IPv4 (`::ffff:`, `::`, NAT64, in either notation) is judged on the embedded address, which is where the socket actually goes. Hosts are unbracketed before the literal check, an out-of-range octet now counts as malformed, and malformed still means private: an address that cannot be classified is not one to connect to

The text is now assembled once in `keystoreUnlockPrompt()` and travels down with the call that needs it - `initialiser_mls` -> `InitMlsOptions` -> `PluginDeviceKeyStore` -> `GetKeyBytesRequest`, flattened so Kotlin and Swift read plain sibling fields. Both are now passed through Paraglide, along with a subtitle, on the enable and disable prompts alike. On iOS only the reason is displayed, so the title is Android-only, but `cancelTitle` maps to `localizedCancelTitle` and is worth sending on both. A test now reads the sources and fails on a `showToast` applied to an unlocalized literal, accepting a template only when it interpolates a message function

The failing link was the second gate. `startLoginFlow` offers biometrics only when the "configured" flag *and* `isKeyPresent(alias)` agree, the latter existing so a reinstall with an empty keystore cannot raise a prompt that could only fail. `isKeyPresent` invoked `plugin:app.tauri.keystore|hasKeyBytes`, but `app.tauri.keystore` is the **Android class identifier** handed to `register_android_plugin`, not the Tauri plugin name (`Builder::new("keystore")`) - so the call resolved no plugin, threw, and a bare `catch { return false }` turned that into "there is no key here". `biometricAttempted` therefore stayed false, the sheet never opened, and since the modal derives its fingerprint button from that same flag, the fallback hid it too. Behind the wrong name there was no route either: no `has_key_bytes` command existed on the Rust side, iOS had no `hasKeyBytes` at all, and the plugin's ACL listed only `store`/`retrieve`/`remove`, so the key-bytes commands would have been refused at the IPC boundary regardless. All four layers are now wired, `BiometricService.disable` stops silently failing to delete the keystore entry for the same reason, and both call sites build their identifier through `keystoreCommands.ts` - whose test reads the Rust sources so a rename, a missing handler registration or a missing ACL entry fails CI instead of shipping
- **Every fresh Tauri install ran on IndexedDB instead of SQLite.** `SqliteStorage.init()` threw `no such column: salt` and `getStorage()` quietly fell back, logging a `console.warn` nobody sees in a WebView. The v1 -> v2 purge still named the `salt` column that the deviceKeyB64 refactor had removed from `CREATE TABLE messages` - and since that branch is gated on `PRAGMA user_version < 2` while a brand-new database starts at 0, it ran on exactly the databases whose schema no longer had the column. An existing install was already past version 2 and skipped it, which is why it never showed in dev. A database created by the `CREATE TABLE IF NOT EXISTS` statements is now stamped at the current schema version and skips every historical branch (detected by reading `sqlite_master` *before* those statements, because `user_version` is 0 for a pre-migration-system database too), and the purge builds its condition from `PRAGMA table_info`, so a dropped column can no longer break a migration that mentions it
- **A new device badged its entire recovered history as unread.** After a history bundle rebuilt the conversation on a fresh device, every message came back marked unread even though most had been read long ago on the old one. The read state was not lost in transport - the bundle carries `readBy`, and our own id is in it, because the read receipt we once sent was persisted by the *peer*, who is the one that answers the history solicitation and returns it to us. The defect was one of order: the bundle is ingested in two steps, and step 1 goes through the add-path, which counts every incoming message as unread because `AddMessageToChatOptions` structurally cannot carry `readBy`; the receipts only arrive with the metadata merge in step 2, which updated the messages but never revisited the counter. The badge was therefore frozen on a value contradicted twenty lines below it. The count is now recomputed after the merge, and clamped with `Math.min` against the current value so a conversation that was open when the bundle landed - already zeroed by the add-path - cannot regain a badge. The startup restore had the same blind spot, deriving unread from "arrived during this replay", which is only a proxy for "not seen yet" and fails on exactly this case; both sites now share one predicate, `isUnreadForUser`. Unchanged on purpose: someone genuinely joining a group appears in no `readBy` and still inherits the full history as unread, which one visit to the conversation clears
- **Being removed from a community was invisible until a reload, and removing one person emptied everybody's sidebar.** Three defects in one event. A community-wide kick (`kickFromWorkspace`) publishes `channel.member.kicked` with a `workspaceId` and no `channelId`, and the client handler opened with `if (!event.channelId) return` - so the one person the event was for did nothing at all with it, and kept a community they no longer belonged to on screen until the next page load. The same handler then acted on the *rest* of the broadcast without ever looking at who was removed: the event goes to every remaining member so their views stay in sync, so kicking one person from a channel deleted that channel from every member's sidebar and IndexedDB. And `channel.member.removed`, which the channel settings panel emits when it takes a user off a single channel, had no client branch at all. Both events are now normalised onto one handler and read through `removalOutcome`, which distinguishes the four real cases: someone else's removal (do nothing), a community-wide removal (purge the workspace, with a toast naming it), the loss of a private channel (purge it, with a toast), and removal from a *public* channel - which costs the user nothing, since a public channel stays readable by every workspace member, so dropping it locally would only be undone by the next reload. That last case is why both channel-scoped events now carry `isPrivate`

### Security
- **A community slug was enough to read every one of its channel keys.** `GET /api/channels/workspaces/by-slug/:slug` returned the raw TypeORM `Channel` entities, and a channel entity carries `masterSecret` - the 32-byte HKDF root that every epoch key of that channel is derived from. It also ran with no membership check whatsoever, so any authenticated Canari user who knew a slug got, for a community they had never joined: its full member roster, its roles, its private channels, and the key material to decrypt the entire history of all of them. A slug is not a secret - every invite link contains one and the invite preview hands it back before you join. The endpoint now requires membership, returns only the channels the caller may actually read (`canAccessChannel`, same rule as the sidebar listing, archived ones excluded), and projects those channels field by field instead of serializing the entity. **Rotating the affected channels' `masterSecret` is not automatic** - a rotation re-keys the channel and is a deliberate act; the exposure window is any deployment before this one
- **An association admin could revoke any other association's cotisants.** `DELETE /api/associations/:id/tags/:tagId` took both parameters and used only the second: `UserTagService.revoke` deleted by primary key with no ownership check, while the guard in front of it verified MANAGE_MEMBERS on `:id` - a permission granted per association. So MANAGE_MEMBERS anywhere, plus a tag id, revoked a cotisation issued anywhere else, and the roster hands those ids out to whoever can read it. The delete is now scoped to `issuingAssocId`, which makes `:id` the authorization rather than decoration: a tag belonging to another association answers 404, exactly as if it did not exist
- **iOS never got the device key out of its keystore.** Follow-up to the change below, caught by dispatching the iOS release workflow as a compile check - the first time any of that Swift/ObjC had been through a compiler. Two defects, both silent: `KeystorePlugin.swift` had a `guard` body that fell through, which is not valid Swift and killed the build outright; and the two background readers pulled the key out of the Keychain with `String(data:encoding:.utf8)`, while `storeKeyBytes` writes the RAW 32 bytes (it base64-decodes its argument, which is why `getKeyBytes` re-encodes on the way out). Random key bytes are almost never valid UTF-8, so the reader returned nil, the key arrived empty and every push fell back to generic text - exactly the failure this work exists to remove. The iOS migration had the mirror error, writing the base64 text where the login path writes bytes, so a migrated install would have disagreed with a fresh one. Android was right on both counts. The contract - raw bytes at rest, base64 across the FFI - is now asserted across all five files by `pushContextFields.test.ts`, since nothing else checks it off macOS
- **The MLS device key no longer sits in cleartext application data.** `push_context.json` held `deviceKeyB64` - the single key that decrypts `mls.bin` and every local message - as plain text, because a background FCM/NSE handler runs with no user present and so cannot satisfy a biometric prompt. The requirement was real; the plaintext file was not the way to meet it, and on iOS that file is swept up by an unencrypted Finder/iTunes backup. The key now lives only in the platform keystore. Android needed no new key: the existing alias is already `setUserAuthenticationRequired(false)`, so the gap was a Context-only reader (`MlsDeviceKeyStore`) - the plugin's own accessor demands an Activity for a purely cosmetic prompt. It deliberately does **not** set `setUnlockedDeviceRequired(true)`, which would make the key unusable while the screen is locked, i.e. exactly when a push arrives. iOS did need a second keychain item (`mls_bg_key_<alias>`, `AfterFirstUnlockThisDeviceOnly`, no access control, shared with the NSE via access group `group.fr.emse.canari`) because the existing one is `.userPresence`-gated and an extension can never satisfy that. A one-shot migration promotes the key at the next app start and strips the field, including the App Group mirror; the background readers have no JSON fallback, so at most one push before that launch shows generic text

Recipient resolution filters on `status='active'`, so the rejoined device was invisible to routing while believing it was a member: its own messages went out, but the history bundle it solicited and every subsequent live message were fanned out to everyone except it. Observed end to end on a wiped device: the peer logged `Full history sent: 33 message(s)` three times over three minutes and the requester never saw a single frame. `validateCommit` now promotes the committing device to `active` when it has no active row

Harmless-looking on the checkpoint paths, where the rejection was only logged - fatal on the fresh-start path, which awaits the save and turned it into `can't access property "length", e is undefined` at login. The three MLS worker contracts (encrypt, catch-up decrypt, key packages) now live in one `mlsWorkerProtocol.ts` imported by both ends, so a renamed field fails `svelte-check` instead of arriving as `undefined`
- **Every install that predated v0.11.0 was locked out of its own messages.** v0.11.0 changed the at-rest envelope of the MLS snapshot (Argon2id + 16-byte salt prefix, keyed on the PIN -> ChaCha20-Poly1305, keyed on the PBKDF2 device key) without shipping a reader for the old one, and neither the MLS IndexedDB (pinned at schema version 1) nor native `mls.bin` was ever versioned - so the old blobs stayed exactly where they were. The first v0.11.x login could not decrypt them and reported "your PIN was changed on another device", offering a recovery that no PIN could satisfy. Both platforms now try the legacy envelope once with the PIN just verified, then re-seal and persist the snapshot under the device key, so local history survives the upgrade. Opening the envelope says nothing about whose state it is: a snapshot left by an interrupted fresh start names the previous device, and that verdict is re-read after the migration so it takes the fresh start it needs instead of escaping init as a raw "Credential identity mismatch"
- **Native MLS was entirely dead on mobile and desktop since v0.11.0.** `TauriMlsService` invoked `initialiser_mls_avec_clef`, `sauvegarder_mls_et_persister_avec_clef` and `generer_key_packages_et_persister_avec_clef`; the Rust commands are registered as `initialiser_mls`, `sauvegarder_mls_et_persister` and `generer_key_packages_et_persister`. Every native MLS init, state save and KeyPackage publication failed with "command not found" - which also meant no Tauri device published a KeyPackage and none appeared under "Connected devices"
- **Biometric sessions could never save their MLS state.** The at-rest key stays in the platform keystore and never reaches JS, so every save and KeyPackage batch arrived with an empty `deviceKeyB64` and was rejected by `decode_base64_to_32_bytes`. `initialiser_mls` now resolves the key once via `MlsManager::resolve_at_rest_key` and caches it in `AppState`, keeping the BiometricPrompt to one per session
- **A credential identity mismatch was reported as "your PIN was changed on another device".** The two failures are now separated by `BaseMlsService.classifyStateLoadFailure`: only a state that will not decrypt pauses for the old-PIN recovery. A mismatch decrypted fine and no PIN can repair it, so it goes straight to a fresh start instead of stranding the user in a recovery they cannot complete
- **The fresh-start branch left the old state on disk**, so the new device id and the stored blob disagreed and the next launch mismatched again - four device ids minted and deleted in eight seconds in production. The fresh state is now persisted before anything else can fail
- **`/settings` and `/login` could bounce off each other indefinitely**, roughly one round trip per second with a token refresh each. The page guard required MLS readiness while the login page only checked the OIDC session, so the two never converged; `/settings` now tests for an account session, and the login page refuses a second identical auto-redirect within 5 seconds
- **Every session minted a new device id and deleted the previous one server-side.** `WebMlsService.init` and `TauriMlsService.init` redeclared the override without the `opts` parameter, silently dropping `noFreshStart`; an undecryptable local state then took the destructive fresh-start branch instead of surfacing the recoverable "state sealed with the old key" signal. The Tauri override also never cleared `initPromise` on failure, so a retry after recovery would have replayed the cached rejection - it now inherits `BaseMlsService.init`

### Changed
- PIN policy simplified back to a single rule - at least 4 characters - applied identically on setup, change, recovery and unlock. The 4-to-8-digit creation rule added in v0.11.1 is gone, along with the numpad and input caps it implied
